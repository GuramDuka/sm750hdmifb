2. Why the reference count is 1 with an empty holders/ directory
--------------------------------------------------------------------------------

  $ cat /sys/module/sm750hdmidrm/refcnt
  1
  $ ls -A /sys/module/sm750hdmidrm/holders/
  (empty)
  $ ls /sys/module/fbcon
  ls: cannot access '/sys/module/fbcon': No such file or directory
  $ grep -nE '^CONFIG_(FB|FRAMEBUFFER_CONSOLE|DRM_FBDEV_EMULATION)' \
      /boot/config-7.3.4-100.fc43.x86_64
  7199:CONFIG_FB=y
  7242:CONFIG_FB_CORE=y
  7244:# CONFIG_FB_DEVICE is not set
  7317:CONFIG_FRAMEBUFFER_CONSOLE=y
  6967:CONFIG_DRM_FBDEV_EMULATION=y

`refcnt` counts non-module users too, and the framebuffer console is built in,
not a module, so it never appears under `holders/`. The console it registers for
the card is a vtconsole:

  $ ls /sys/class/vtconsole/
  vtcon0  vtcon1
  $ cat /sys/class/vtconsole/vtcon0/name
  (S) VGA+
  $ cat /sys/class/vtconsole/vtcon0/bind
  0
  $ cat -A /sys/class/vtconsole/vtcon1/name
  (M) frame buffer device$
  $ cat /sys/class/vtconsole/vtcon1/bind
  1
  $ cat /proc/consoles
  tty0  -WU (EC p ) 4:1
  $ cat /sys/class/tty/tty0/active
  tty1

`(M)` marks the vtconsole whose backing fb_info comes from a module, and the
bind value 1 is the reference. Writing 0 to that `bind` file releases it, and
writing 1 takes it back. The driver's fbdev client is registered from
`drm_client_setup` at src/sm750_drm.c:5266, after `drm_dev_register` at
src/sm750_drm.c:5262, which is why the version attribute can appear a moment
after a load returns and why the helper waits for it in a bounded loop.

No process holds the card, so the reference is not a leaked client either:

  $ stat -L -c '%d %i' /dev/dri/card0
  9 297
  $ (scan of /proc/[0-9]*/fd for links resolving to card0)
  0 holders

--------------------------------------------------------------------------------
3. How the target vtconsole is identified, and why not better
--------------------------------------------------------------------------------

Kernel 7.3.4 exposes no way to attribute a vtconsole to a driver:

  $ ls /sys/class/vtconsole/vtcon1/
  bind  name  power  subsystem  uevent

There is no `device` link, so the usual "walk the device tree to the driver"
rule cannot be used. The framebuffer class is equally unhelpful because no
framebuffer character device is built:

  $ ls /sys/class/graphics/
  fbcon
  $ ls /sys/class/graphics/fb[0-9]*
  ls: cannot access '/sys/class/graphics/fb[0-9]*': No such file or directory
  $ ls /dev/fb*
  ls: cannot access '/dev/fb*': No such file or directory

`CONFIG_FB_DEVICE` is unset, so `/dev/fb0` and `fb0` do not exist and
`/proc/fb` is absent. What remains measurable is the class glob plus the PCI
side of the card:

  $ readlink -f /sys/bus/pci/devices/0000:01:00.0/driver
  /sys/bus/pci/drivers/sm750hdmidrm

The implemented basis is therefore: exactly one vtconsole whose `name` contains
`frame buffer device`, cross-checked against the `0000:01:00.0` driver being
`sm750hdmidrm`. Zero candidates and more than one candidate are refusals that
list what was found. This is stated by the helper itself as the `basis:` line
of `sm750-vt show`, and it is deliberately not a hardcoded `vtcon1`: on a host
with two framebuffer consoles the index would be a guess.

--------------------------------------------------------------------------------
4. What the helper does, in order
--------------------------------------------------------------------------------

`show` - no state change, runs unprivileged: prints each vtconsole with its
bind value, the resolved target and the basis string, the current bind, the
module version/srcversion/refcnt, the active tty, the card node with its
dev:inode, and the holder count with a `pid:comm` line per holder.

`off` - the reload, root only:

  1. resolve the target (section 3); refuse if not root
  2. refuse if `bind` already reads 0, naming the `on` mode
  3. refuse if any process holds the card, printing `pid:comm` per holder -
     `modprobe -r` would fail with "is in use" and would not say who
  4. announce: target, basis, and that there will be no text console until the
     reload ends
  5. write 0 to `$TARGET/bind`, read it back
  6. `modprobe -r sm750hdmidrm`; on failure restore the console, say the console
     was restored and nothing changed, exit 1
  7. `modprobe sm750hdmidrm`; on failure exit 1 (the console stays detached
     only for the length of the failing run; the EXIT trap restores it)
  8. wait up to 20 x 0.1 s for `/sys/module/sm750hdmidrm/version`; if it never
     appears, exit 3 with "is missing after the load"
  9. write 1 to `$TARGET/bind`, read it back; exit 3 if the write does not take
 10. print the reloaded version, srcversion and refcnt, the restored bind and
     the card's driver

One EXIT trap covers every non-zero path: it re-binds fbcon if this run
detached it and then re-raises the original status. The restore function ends
in an explicit `return` because a trap whose last command can fail silently
replaces the real exit status.

`on` - recovery: refuses if `bind` already reads 1, otherwise writes 1, reads it
back, prints the module line.

Exit codes: 0 success, 1 environment or restore problem, 2 usage error, 3 a
measured expectation failed.

7. The first live attempt, and what it changed (defect A51)
--------------------------------------------------------------------------------

The helper was installed on the host and run by the owner through the existing
allowlist lines. The reload is STILL NOT YET OBSERVED: attempt 1 failed after
detaching the console, restored everything, and left the machine unchanged.
Verbatim output of `sm750-vt off`:

```
sm750-vt: target /sys/class/vtconsole/vtcon1 (basis: sole framebuffer vtconsole on the host, with the sole sm750hdmidrm card (card0, 0000:01:00.0); not by a hardcoded index)
sm750-vt: detaching fbcon; there will be no text console until the reload ends
sm750-vt: fbcon detached, bind=0
modprobe: FATAL: Module sm750hdmidrm is in use.
sm750-vt: fbcon re-bound to /sys/class/vtconsole/vtcon1 (bind=1)
sm750-vt: modprobe -r sm750hdmidrm failed; the console was restored and nothing changed
rc=1
```

What was measured right after, all read-only:

  * `cat /sys/module/sm750hdmidrm/refcnt` = 1, and `ls -A
    /sys/module/sm750hdmidrm/holders/` prints nothing: the holder is not a
    module.
  * `grep sm750hdmidrm /proc/modules` = `sm750hdmidrm 200704 1 - Live ... (OE)`.
    The dependent lines `drm_vram_helper ... 1 sm750hdmidrm` and
    `drm_ttm_helper ... 3 nvidia_drm,sm750hdmidrm,drm_vram_helper` are ordinary
    dependencies.
  * No userspace holder: the card node `/dev/dri/card0` is device inode 9:297
    (`/dev/dri/renderD128` is 9:296) and a scan of `/proc/[0-9]*/fd` for that
    inode finds nothing.
  * `dmesg` carries `sm750hdmidrm 0000:01:00.0: [drm] fb0: sm750hdmidrmdrm frame
    buffer device`, and each failed attempt logged `Console: switching to
    colour VGA+ 80x25` followed by `Console: switching to colour frame buffer
    device 128x48`.
  * `/sys/class/vtconsole/vtcon1/name` is `(M) frame buffer device` and
    `vtcon1/bind` reads 1 again after the restore; `/sys/class/graphics/`
    contains only `fbcon`, so there is no `fb0` class device to unregister.

Conclusion: `vtcon*/bind` 0 detaches the console from the framebuffer but does
not release the reference the registered framebuffer holds on the module. The
reference is dropped by removing the device: writing the BDF to
`/sys/bus/pci/drivers/sm750hdmidrm/unbind` runs the driver's remove path, which
unregisters the DRM device and the fbdev client registered by
`drm_client_setup` (`src/sm750_drm.c:5266`, after `drm_dev_register` at
`:5262`).

What changed in the helper as a result (defect A51, tools/sm750-vt.sh):

  * `off` writes the BDF to `/sys/bus/pci/drivers/sm750hdmidrm/unbind` after the
    console detach and before `modprobe -r`, and verifies the device's driver
    link no longer resolves; a bind is verified by that link resolving back.
  * The module refcount is printed before anything is touched and again right
    after the unbind; a refcount that is still non-zero fails the run with that
    number instead of a bare modprobe error.
  * After the load the device is bound again if the driver core did not
    re-probe it, and the console is re-bound only after that read-back.
  * The single EXIT trap now restores module, then device, then console, and is
    disarmed by `FINISHED=1` so a successful run never undoes itself.
  * The driver directory is a fixed path rather than a `readlink` of the device
    link, because the module owns it and the link disappears with the unload.

Nothing privileged was performed to write this section: no sysfs write, no
modprobe, no sudo, no compositor. Attempt 2 has not run either, because it needs
the refreshed helper installed by the owner. The `NOT YET OBSERVED` list of
section 6 therefore still stands in full, with one item now measured rather
than assumed: the console detach alone is not sufficient.

8. The holder scan matched a node name, and why that was wrong
--------------------------------------------------------------------------------

Found 2026-11-26 while reading the helper, before any second live attempt.
Nothing privileged was performed to confirm it: no sysfs write, no modprobe, no
sudo, no compositor. The bug is in `holders()`, at what was line 173 of
`tools/sm750-vt.sh`:

```
case $t in *card0*) ;;
*) continue ;;
esac
```

`$t` is the readlink target of an entry under `/proc/<pid>/fd`. The scan
therefore recognised a holder only while the DRM node happened to be named
`card0`. The name is not stable across a probe: the measured by-path links on
this host read

```
$ readlink /dev/dri/by-path/pci-0000:01:00.0-card
../card4
$ readlink /dev/dri/by-path/pci-0000:01:00.0-render
../renderD132
$ stat -L -c '%d:%i' /dev/dri/by-path/pci-0000:01:00.0-card
9:1582
$ stat -L -c '%d:%i' /dev/dri/by-path/pci-0000:01:00.0-render
9:1581
```

Section 2 recorded the same node as `/dev/dri/card0` with inode `9 297`, so
both the name and the inode were re-issued when the module was re-probed. A
name match fails silently in exactly the case that matters: when the module is
held. The observed consequence would be the refusal message of step 3 of
section 4 printing an EMPTY holder list, which states that nothing holds the
card while the refcount says otherwise, and hides the process an operator needs
to see.

Measured, read-only, as user `coder` (which holds ACL `rw` on the card node, so
no root is needed):

```
$ sh tools/sm750-vt.sh show
...
card:         /dev/dri/by-path/pci-0000:01:00.0-card -> /dev/dri/card4 inode 9:1582
render:       /dev/dri/by-path/pci-0000:01:00.0-render -> /dev/dri/renderD132 inode 9:1581
holders:      0 userspace processes hold the card

$ ( exec 3</dev/dri/by-path/pci-0000:01:00.0-card; sleep 30 ) &
$ sh tools/sm750-vt.sh show | tail -2
holders:      1
  969720:sleep card4

$ ( exec 3</dev/dri/by-path/pci-0000:01:00.0-render; sleep 30 ) &
$ sh tools/sm750-vt.sh show | tail -2
holders:      1
  974959:sleep renderD132
```

The pid of the synthetic reader differs per run (a later repeat measured
`1031518:sleep card4`); it is the sleeping subshell, not the shell that started
it.

The old glob over the same fd table with pid 969720 alive printed nothing,
which is the false negative reproduced directly.

The fix, in the tree: `node_inode()` resolves a path with `stat -L -c '%d:%i'`,
`card_inode()` and `render_inode()` resolve the two by-path links (the render
link may legitimately be absent), and `holders()` compares each fd target's
`dev:inode` against both, printing `pid:comm node` with the node name used only
for display. `show` gained a `render:` line and now prints the card and render
nodes the by-path links resolve to, because those names are diagnostic and
change per probe. The basis string no longer names `card0`.

Gate: `tests/check-vt-helper.sh` gained section l (the by-path links, the
`stat -L -c` form, the identity comparison, the printed node name, and a check
that no `*card[N]*` glob survives outside a comment) and the planted control
`holder-scan-name-glob`, which rewrites the comparison back into the old glob
and is rejected with `FAIL: l: the fd scan must compare node identity, not a
node name`. The gate now reads thirteen assertions and ten planted controls.

NOT YET OBSERVED: this section is a read-only measurement of the helper and of
sysfs. The reload itself has still not succeeded, and the refusal path has not
been exercised on the host against a real holder; pid 969720 above is a
synthetic reader started for the measurement, not the process that actually
holds the module reference.

9. The second live attempt: the reference survives a full device unbind (defect A52)

Section 7 ended with a sequence that detaches the console and then unbinds the
PCI device, and with the assumption that the unbind releases the reference the
framebuffer holds. The owner installed that helper
(`/usr/local/sbin/sm750-vt`, 411 lines, sha256
`ebcece0675240834e0fab97528be1bbfc8b62ba3f5b2d24847223aeda1f14916`, matching
the tree) and ran it. The sequence ran to completion and the unload was still
refused:

```
sm750-vt: refcnt before any change: 1
sm750-vt: fbcon detached, bind=0
sm750-vt: unbinding 0000:01:00.0 from sm750hdmidrm to release the framebuffer
sm750-vt: device unbound, refcnt after the unbind: 1
sm750-vt: the module refcount is still 1 after unbinding the device, so
          something other than the framebuffer holds it (holders directory: );
          modprobe -r cannot succeed
sm750-vt: 0000:01:00.0 re-bound to sm750hdmidrm
sm750-vt: fbcon re-bound to /sys/class/vtconsole/vtcon1 (bind=1)
rc=1
```

The restore path did its job: the device was bound again, the console was bound
again, and the module stayed at 0.6.5 rather than being left half-removed. What
that run and the measurements around it establish:

`refcnt` is 1 before the detach, after the detach, and after the unbind.

```
$ cat /sys/module/sm750hdmidrm/refcnt
1
$ ls -A /sys/module/sm750hdmidrm/holders/
$ grep '^sm750hdmidrm ' /proc/modules
sm750hdmidrm 200704 1 - Live 0xffffffffc0a3d000 (OE)
```

No userspace holder exists. A whole-host scan of `/proc/[0-9]*/fd` finds no
process holding any `/dev/dri/*` node, and none holding the SM750 card or render
node by inode, so the reference is not an open file description.

`1` is a real reference on this host, not a counting artefact. Every
`/sys/module/*/refcnt` was read: 34 modules read `0`, 36 read `1`, and the ones
at `1` are modules with something genuinely attached (`binfmt_misc`,
`drm_vram_helper`, `i2c_algo_bit`, `i2c_smbus`). The `nvidia` family is not a
counter-example, because its counts come from module-to-module dependencies
listed in `holders/` (`nvidia` 427, `nvidia_drm` 60, `nvidia_modeset` 15), and
this module has none.

The module itself takes no reference and registers nothing else. `grep` over
`src/*.c src/*.h` finds no `try_module_get`, `module_get` or `module_put`, and
no `i2c_add_driver`, `i2c_register_driver`, `i2c_add_adapter`,
`i2c_new_client`, `platform_driver_register`, `auxiliary_driver`,
`module_i2c_driver`, `module_platform_driver`, `drm_panel_init`, `serio` or
`input_register`. `module_pci_driver(sm750_pci_driver)` at `src/sm750_drm.c:5375`
is its only registration; the SiI9022 is driven by bit-banging MMIO
(`sm750_sw_i2c_init` at `src/sii902x.c:771`), not through an i2c client, and
`/sys/bus/i2c/devices` holds only other drivers' entries.

The detach is real. When the trap rebound the device, the kernel re-probed it
completely:

```
[13925.142750] Console: switching to colour VGA+ 80x25
[13925.221212] sm750hdmidrm 0000:01:00.0: DMA1 IRQ was not delivered; reverting to completion polling
[13925.392261] [drm] Initialized sm750hdmidrm 0.6.5 for 0000:01:00.0 on minor 4
[13928.418802] Console: switching to colour frame buffer device 128x48
[13928.418821] sm750hdmidrm 0000:01:00.0: [drm] fb0: sm750hdmidrmdrm frame buffer device
[13928.918794] sm750hdmidrm 0000:01:00.0: full-frame backbuffer staging enabled (1572864 bytes per buffer)
[13928.962343] sm750hdmidrm 0000:01:00.0: painted a test card: no client has produced a frame (test_pattern=auto)
```

The DRM minor advanced across those cycles - it was `0` at boot and is `4` now,
with three `on minor 4` lines in the boot log - which only happens when the DRM
device is registered again after being torn down. So the unbind is not a silent
no-op, and the missing `drm_dev_unregister()` in `sm750_pci_remove`
(`src/sm750_drm.c:5300-5313`) is not the cause: the device does come apart.

The remove path, for the record, calls `drm_kms_helper_poll_fini`,
`drm_dev_unplug`, `sm750_test_pattern_cancel`, `drm_atomic_helper_shutdown`,
`sm750_vblank_timer_stop` and `sm750_sii902x_shutdown`, and neither
`drm_dev_unregister` nor `drm_dev_put`. The latter would be wrong: the device
comes from `devm_drm_dev_alloc` at `src/sm750_drm.c:5050` and devres owns the
put (`include/drm/drm_drv.h:460-461`).

What is not known: which kernel object holds the reference. A structure in the
DRM core that outlives the driver detach on this kernel series is the shape that
fits, but nothing measured here identifies one. `drm_dev_unregister()` was
considered as a fix and rejected, because the installed headers give it no
documented reference semantics and the change could not be measured on this
host; a fix that cannot be measured is not a fix. The defect is recorded as open
in `docs/DEFECTS.md` (A52) with no code change, and the helper keeps printing
the refcount so the failure is reported rather than guessed at.

NOT YET OBSERVED at the time of this section: any successful hot reload. The
working path to a newly built module on this host was still a reboot, which
loads the module DKMS already built
(`/lib/modules/7.3.4-100.fc43.x86_64/extra/sm750hdmidrm.ko.xz`, 71804 bytes,
`modinfo -F version` 0.6.7, srcversion `FF25FF6111B7C6D174A72F8`).
