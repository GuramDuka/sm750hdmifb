2. WHERE THE EINVAL COMES FROM: TWO INDEPENDENT GATES, BOTH GENERIC DRM
========================================================================================

The driver registers no framebuffer-creation callback of its own; it uses the
generic GEM helper:

  src/sm750_drm.c:3243-3244   static const struct drm_mode_config_funcs
                              sm750_mode_config_funcs = { .fb_create = drm_gem_fb_create, ... }
  src/sm750_drm.c:3249-3250   static const struct drm_mode_config_funcs
                              sm750_shadow_mode_config_funcs = { .fb_create = drm_gem_fb_create_with_dirty, ... }
  src/sm750_drm.c:3432-3433   selected by `sdev->shadow_scanout`

So every rejection below is produced by DRM core/helper code acting on limits the
driver declared. There is no driver-local EINVAL on this path.

GATE 1 (fires first): framebuffer height outside the declared range.

  /tmp/opencode/drm_framebuffer.c:279-282, in drm_internal_framebuffer_create():

      if ((config->min_height > r->height) || (r->height > config->max_height)) {
          drm_dbg_kms(dev, "bad framebuffer height %d, should be >= %d && <= %d\n",
                      r->height, config->min_height, config->max_height);
          return ERR_PTR(-EINVAL);
      }

  The width twin is the preceding block, drm_framebuffer.c:274-277
  ("bad framebuffer width %d, should be >= %d && <= %d"). Order inside the function:
  flags :270-273, width :274-277, height :279-282, modifier support :284-287,
  format table :292-295, framebuffer_check() :301, driver fb_create() :305.
  Because height is validated BEFORE fb_create() is called, a too-tall request dies
  here whatever its pixel format is.

  The values are the driver's own declaration:
    src/sm750_drm.c:3435   drm->mode_config.min_height = 200;
    src/sm750_drm.c:3437   drm->mode_config.max_height = SM750_DRM_MAX_HEIGHT;
    src/sm750_drm.c:95     #define SM750_DRM_MAX_HEIGHT 1152
  Confirmed at run time by DRM_IOCTL_MODE_GETRESOURCES on the loaded driver:
    "mode_config from DRM_IOCTL_MODE_GETRESOURCES: width 320..2560, height 200..1152"

  2048 > 1152, so gate 1 rejects the f_16 request with -EINVAL, which is the errno 22
  IGT records.

GATE 2 (would fire next if gate 1 were relaxed): pixel format not offered by any plane.

  /mega/tmp/sm750/t15/gemfb.c:166-171, in drm_gem_fb_init_with_funcs():

      if (drm_drv_uses_atomic_modeset(dev) &&
          !drm_any_plane_has_format(dev, mode_cmd->pixel_format,
                                    mode_cmd->modifier[0])) {
          drm_dbg_kms(dev, "Unsupported pixel format %p4cc / modifier 0x%llx\n",
                      &mode_cmd->pixel_format, mode_cmd->modifier[0]);
          return -EINVAL;

  The gate is live on this driver because it advertises atomic modesetting:
    src/sm750_drm.c:3367 and :3381
      .driver_features = DRIVER_GEM | DRIVER_MODESET | DRIVER_ATOMIC
  and because the plane format lists are:
    src/sm750_drm.c:3423   static const u32 formats[] = { DRM_FORMAT_XRGB8888 };
    src/sm750_drm.c:3424   static const u32 cursor_formats[] = { DRM_FORMAT_ARGB8888 };
  DRM_FORMAT_RGB565 appears in neither, so drm_any_plane_has_format() returns false
  for it.

GATE 3 (checked, does NOT fire): GEM object smaller than the minimum size.

  gemfb.c:186-193
      min_size = (height - 1) * mode_cmd->pitches[i]
               + drm_format_info_min_pitch(info, i, width)
               + mode_cmd->offsets[i];
      if (objs[i]->size < min_size) { ...; ret = -EINVAL; }

5. VERDICT
========================================================================================

  The driver is not wrong. The test is not exceeding a hardware limit.

  What the subtest exceeds is the driver's KMS interface contract, in two declared
  dimensions at once:

    (a) pixel format: the primary plane advertises only DRM_FORMAT_XRGB8888
        (src/sm750_drm.c:3423). RGB565 is not a KMS format on this driver; it is an
        internal upload/scanout format. docs/MODES.md:91-96 states the contract:
        "Userspace always renders XRGB8888 source buffers. The default
        rgb565-bbdither scanout converts only changed output regions to two-byte
        RGB565 immediately before upload." The conversion is also the
        `scanout_format` module parameter (docs/PARAMETERS.md:19, default
        `rgb565-bbdither`; accepts xrgb8888 and rgb565). The driver converts
        internally; it never accepts a 16-bit source buffer from userspace.

    (b) framebuffer height: max_height is declared as 1152
        (src/sm750_drm.c:95 and :3437), which is the height of the tallest mode in
        the supported catalogue (docs/MODES.md:76-86, 2048x1152). The mode validator
        enforces the same number for display modes at src/sm750_drm.c:1201
        (`if (hardware_mode->vdisplay > SM750_DRM_MAX_HEIGHT) return MODE_BAD_VVALUE;`).

  Both are deliberate: the shadow/scaling path is sized from those two constants
  (src/sm750_drm.c:3640-3641, :3644-3646 allocate the snapshots as MAX_WIDTH*MAX_HEIGHT
  and PHYSICAL_MAX_WIDTH*MAX_HEIGHT), and the pipeline never scans more lines than
  the tallest supported mode.

  Decisive datasheet constraint (proves the limit is driver policy, not silicon):
  DS-1 rev 1.4 p151 PANEL_FB_WIDTH gives a 16368-byte pitch ceiling, p152
  PANEL_WINDOW_HEIGHT gives a 4095-line window and p153 PANEL_PLANE_BR gives an
  11-bit bottom coordinate (2048 lines), with 64 MiB of VRAM. A 1024x2048
  XRGB8888/RGB565 framebuffer at 2048-byte pitch is inside all of them. The
  hardware would accept it; the driver declines to expose it.

  IGT-side observation (for the IGT maintainers, not a driver action): size_tests()
  gates the C8 request on igt_display_has_format_mod() at kms_addfb_basic.c:597 but
  issues the RGB565 request at :594 unconditionally. Any driver whose primary plane
  does not advertise RGB565 fails size-max at :594 for that reason alone, whatever
  its size limits are. This driver is exactly such a driver.

  Disposition: accepted / correct-by-design. No code change is required for
  correctness, and no code change is recommended:
    - Raising max_height alone cannot make the subtest pass, because gate 2 rejects
      RGB565 independently (probe [2]). It would only widen the declared KMS surface
      beyond anything the pipeline scans out.
    - Adding RGB565 to the primary plane's format list would require the scanout
      path to consume 16-bit source rows; every converter in the driver assumes u32
      XRGB8888 source rows (src/sm750_drm.c:1991-2015, dither_source_line is u32 at :270).
      That is a feature, not a defect fix, and it contradicts the documented
      contract in docs/MODES.md:91-96.

  Documentation change (the concrete recommendation):
    docs/MODES.md, "Physical catalogue limits" section: record that a KMS
    framebuffer is limited to the declared mode_config range of 320x200 to
    2560x1152 (src/sm750_drm.c:3434-3437), that max_width 2560 exceeds the
    2048-pixel scanout catalogue because it is consumed by the downscale path,
    that the primary plane's only KMS format is XRGB8888 and RGB565 exists only as
    the internal scanout conversion, and that IGT kms_addfb_basic/size-max
    consequently cannot pass on this driver (it asks for a 1024x2048 RGB565
    framebuffer at kms_addfb_basic.c:594 without a format probe).
    Optional, if a reader needs the mapping in code: a comment at
    src/sm750_drm.c:3437 explaining that max_height is the tallest catalogue mode
    rather than the 2048-line PANEL_PLANE_BR ceiling.
