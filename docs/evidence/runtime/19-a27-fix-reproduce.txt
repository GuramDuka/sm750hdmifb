T20 - A27 FIX: POST-FIX REPRODUCTION, 108 ATTEMPTS
===================================================

Question this file answers: with the fixed module loaded, does the A27 cascade
still appear when the trigger that produced it is run?

Trigger (unchanged from T16, the shape that worked): send SIGINT to a kmscube
300 ms into its first commit, then run `modetest -s 35@38:1024x768-60`, then
restore 1920x1080. The `-110` that A27 turns into a WARNING lands on the
1920x1080 restore that drm_release issues when modetest closes the device.

Symptom markers counted per attempt (a27_hits): the drm_atomic_helper WARNING,
`flip_done timed out`, `commit wait timed out`, `refcount_t: underflow` and
`use-after-free`. The fail-path message is counted separately (failpath): it is
not a symptom, it is the driver reporting that the modeset did not complete,
and after the fix it is expected to occur without any of the markers.

Host: kernel 7.3.4-100.fc43.x86_64, user coder (uid 1005), unprivileged
(/dev/dri/card0 carries ACL user:coder:rw-, so kmscube and modetest run without
root). Module under test: sm750hdmidrm 0.6.0, srcversion
07E8F503FC7D839EEC5EE64, i.e. the fixed build delivered in
18-a27-fix-install.txt. Harness: /mega/tmp/sm750/t20/repro.sh; raw log
/mega/tmp/sm750/t20/logs/reproduce.log; the dmesg window of every attempt that
saw the fail path is kept in /mega/tmp/sm750/t20/repro-windows.txt.

7. WHAT THIS DOES NOT PROVE
----------------------------
It does not identify which of the five fallible calls in sm750_program_mode
returns -110 (GAP-B8 stays open); it does not raise or lower any framebuffer or
plane limit; and it does not make the -110 rarer. It shows that when the -110
happens, the commit finishes, vblank accounting is back on, and neither the
WARNING, the 30 s of stalled commits nor the refcount underflow follow.
