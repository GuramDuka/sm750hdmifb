# 36 - Render node (DRIVER_RENDER) for the SM750 DRM driver
#
# Recorded: 2026-11-25 (UTC session of the 0.6.5 render-node change)
# Scope: src/sm750_drm.c (two driver_features lines, the version define) and
# the release bump to 0.6.5. Gate: tests/check-render-node.sh.
#
# ---------------------------------------------------------------------------
# 1. Why
# ---------------------------------------------------------------------------
# KWin 6.7.5 refuses a DRM device whose node set has no render node. The
# literal string is in the installed library:
#
#   $ strings -a /usr/lib64/libkwin.so.6.7.5 | grep -F 'without a render node'
#   Skipping device %s without a render node
#
# So /dev/dri/card0, the SM750 at PCI 0000:01:00.0, is skipped before it is
# ever opened. Advertising DRIVER_RENDER gives that userspace a render node to
# open. It is not a claim of 3D or GL capability.
#
# ---------------------------------------------------------------------------
# 2. Kernel facts relied on (quoted from the installed headers)
# ---------------------------------------------------------------------------
# /usr/src/kernels/7.3.4-100.fc43.x86_64/include/drm/drm_drv.h:71-78
#
#	DRIVER_MODESET			= BIT(1),
#	/**
#	 * @DRIVER_RENDER:
#	 *
#	 * Driver supports dedicated render nodes. See also the :ref:`section on
#	 * render nodes <drm_render_node>` for details.
#	 */
#	DRIVER_RENDER			= BIT(3),
#
# /usr/src/kernels/7.3.4-100.fc43.x86_64/include/drm/drm_ioctl.h:112-121
#
#	DRM_ROOT_ONLY		= BIT(2),
#	/**
#	 * @DRM_RENDER_ALLOW:
#	 *
#	 * This is used for all ioctl needed for rendering only, for drivers
#	 * which support render nodes. This should be all new render drivers,
#	 * and hence it should be always set for any ioctl with DRM_AUTH set.
#	 * Note though that read-only query ioctl might have this set, but have
#	 * not set DRM_AUTH because they do not require authentication.
#	 */
#	DRM_RENDER_ALLOW	= BIT(5),
#
# Consequence for this device: DRIVER_RENDER is a node-set flag only. The
# per-ioctl DRM_RENDER_ALLOW flag decides what an unauthenticated render file
# descriptor may call. The driver sets no DRM_AUTH-exempt render path of its
# own; the render node therefore reaches the core GEM/dumb-buffer
# (DRM_IOCTL_MODE_CREATE_DUMB and friends) and PRIME/dma-buf handle and fd
# transfer ioctls plus the read-only query ioctls, which is all the hardware can
# back. SM750 has no 3D engine, no command submission and no shader, so there
# is nothing further to expose. DRIVER_MODESET is kept on the same
# driver_features line: a render-only device would lose card0, its connectors
# and every modeset.
#
# Mesa: there is no SM750 Gallium driver. The only paths that can drive this
# card are swrast/kms_swrast, so the render node does not make Plasma work by
# itself; kwin additionally needs a logind seat and a GL-capable context.
#

# /dev/dri/renderDN character device and write access for the invoking user.
#
# ---------------------------------------------------------------------------
# 7. Risk of advertising DRIVER_RENDER without a 3D engine
# ---------------------------------------------------------------------------
# - A userspace probe may open the node, see a DRM device, and assume a
#   working rendering stack. That assumption is wrong here: there is no 3D
#   engine and no Mesa driver. The node's ioctl set is limited to what the
#   core marks DRM_RENDER_ALLOW, so a probe that actually tries to render
#   fails at the ioctl or at buffer allocation rather than silently.
# - The node consumes one minor number and one udev node (226,64+k) for a
#   device that cannot render. Nothing in the driver changes.
# - kwin will now get a file descriptor and proceed to its next requirement
#   (a logind seat and a GL context), so it may fail later and differently.
#   That is still an improvement over being skipped before any open, but it
#   does not by itself make Plasma start.
# - DRIVER_MODESET is deliberately retained. Dropping it to make the device
#   "render only" would remove card0 and every disconnect; the gate fails any
#   line that sets DRIVER_RENDER without DRIVER_MODESET for that reason.
#

# ---------------------------------------------------------------------------

# loaded; section 6 is kept as the historical "not yet observed" record.
#
#   $ cat /sys/module/sm750hdmidrm/version
#   0.6.5
#
# 8.1 The node
# ------------
#   $ ls -l /dev/dri/renderD131
#   crw-rw-rw- 1 root render 226, 131 /dev/dri/renderD131
#
#   $ ls -l /sys/class/drm/card0/device/drm/
#   drwxr-xr-x card0
#   lrwxrwxrwx controlD64 -> card0
#   drwxr-xr-x renderD131
#
# The SM750 slot now has exactly three nodes: card0, controlD64 and
# renderD131. The other render nodes on the host (renderD128, 129, 130) still
# belong to the NVIDIA cards and are unchanged.
#
# 8.2 Identity of each node
# -------------------------
# A python3 ctypes probe issued DRM_IOCTL_VERSION (0xC0406400) against both
# nodes:
#
#   /dev/dri/renderD131  driver='sm750hdmidrm' ver=0.6.5
#                        desc='SM750G10 SiI9024A HDMI DRM shadow driver'
#   /dev/dri/card0       driver='sm750hdmidrm' ver=0.6.5
#                        desc='SM750G10 SiI9024A HDMI DRM shadow driver'
#
# Both nodes opened O_RDWR as the unprivileged user. The description is the
# `.desc` of the shmem shadow driver struct, so the observation also settles
# which of the two drm_driver instances is the instantiated one: it is
# sm750_shadow_drm_driver, not the TTM struct. Both structs carry
# DRIVER_RENDER (src/sm750_drm.c:4527 and :4542), so the node does not depend
# on which one binds.
#
# 8.3 kwin_wayland outcome: still refused
# ---------------------------------------
# kwin_wayland 6.7.5, measured in /mega/tmp/sm750/wl/kwin2.out:
#
#   kwin_core: Ignoring render device /dev/dri/renderD131 without hardware acceleration
#   kwin_core: Added render device /dev/dri/renderD128
#   kwin_core: Failed to open /dev/dri/card0 device (Operation not permitted)
#   kwin_wayland_drm: Failed to open drm device /dev/dri/card0
#   kwin_wayland_drm: No suitable DRM devices have been found
#   exit code 1
#
# The "Operation not permitted" is not a failed syscall. The full strace
# /mega/tmp/sm750/wl/kwin5.strace contains exactly one EPERM, and it is
# unrelated to the card:
#
#   futex(0x7fffffffc8b4, FUTEX_UNLOCK_PI_PRIVATE) = -1 EPERM
#
# A file-tracing run (/mega/tmp/sm750/wl/kwin4.strace) shows kwin never opens
# card0 at all: it only stats it and follows the DRM class link, then opens
# only the render nodes.
#
#   newfstatat(AT_FDCWD, "/dev/dri/card0", {st_mode=S_IFCHR|0660, ...}, 0) = 0
#   readlink("/sys/devices/pci0000:00/0000:00:01.0/0000:01:00.0/drm/card0", ...)
#
# So the message is a library-level permission-model verdict formed before any
# open, not an errno from an open call.
#
# 8.4 Two independent barriers remain
# -----------------------------------
# Neither barrier is a driver defect and neither is addressed by DRIVER_RENDER.
#
# (a) No hardware acceleration for the node. Mesa ships no SM750 driver:
#     $ ls /usr/lib64/dri/    # no sm750, smi or silicon entry; swrast and
#                             # kms_swrast are provided by libdril_dri.so
#     and an EGL device-platform probe (eglQueryDevicesEXT) returns zero
#     devices. kwin's "without hardware acceleration" line is this fact.
#
# (b) No logind seat. `loginctl list-seats` lists only seat0 and the service
#     account's sessions have no seat. /usr/lib64/libkwin.so.6.7.5 carries
#     KWin::LogindSession, DBusLogindSeat and the string
#     "The session is not active", which is the check it applies next.
#
# Attempts that changed nothing: KWIN_WAYLAND_NO_PERMISSION_CHECKS=1 with
# KWIN_DRM_DEVICES=/dev/dri/card0 and LIBSEAT_BACKEND=noop. kwin 6.7.5 has no
# --drm-device option either (`kwin: Unknown option 'drm-device'.`).
#
# 8.5 Where Plasma does run on this driver
# ----------------------------------------
# X11 is the route: Xorg 21.1.26 started as
# `/usr/libexec/Xorg :1 -config ... -sharevts -novtswitch vt0` drives card0 at
# 1920x1080, plasmashell and kwin_x11 run, and window management works
# (wmctrl moved a window on request). Compositing is off because the server's
# GLX is DRISWRAST and lacks GLX_EXT_texture_from_pixmap, which aborts
