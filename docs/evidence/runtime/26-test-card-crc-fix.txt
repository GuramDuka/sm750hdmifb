1. The defect in one paragraph
------------------------------

T37 shipped a one-shot flag, `test_pattern_fresh`, meant to stop the enabling
commit's own plane update from overwriting the freshly painted card. It could
not do that job. `sm750_pipe_update()` is called from `commit_planes()`, which
the default atomic tail (`drm_atomic_helper_commit_tail()`,
`drm_atomic_helper.c:1984-2003`) runs before `commit_modeset_enables()`;
`sm750_pipe_enable()` is the modeset enable. The flag was set after the update
it existed to skip, so the first update it swallowed was the *client's* first
present, and the `goto event` around it also jumped over the
`sm750_test_pattern_cancel()` that follows, leaving the 5 s palette rotation
running on a pipe a client had taken over. The rotating card kept rewriting the
262144-byte window `sm750_scanout_crc32()` reads in 256-byte chunks, so one
readback entry straddled two palettes and the harness reported
`FAIL: CRC is not stable for a static frame: 3 distinct values in 12 frames`.

2. R1 - a CRC source owns the window
------------------------------------

Three edits in src/sm750_drm.c:

- `sm750_crc_enable()` now cancels the card after it marks the source armed and
  before it arms the interrupt:

      sdev->crc_enabled = true;                                  /* :3291 */
      sdev->crc_warned = false;
      sm750_test_pattern_cancel(sdev);                           /* :3295 */
      ret = sm750_crc_arm(sdev);                                 /* :3296 */

  The cancel sits inside the existing `crc_mutex` section and takes no
  `mode_lock`, so no lock order changes. A forward declaration of
  `sm750_test_pattern_cancel()` was added above `sm750_crc_enable()` (:3270)
  because the definition lives in the test-card block further down.

- `sm750_test_pattern_should_paint()` gained the device and a first-statement
  refusal:

      if (READ_ONCE(sdev->crc_enabled))                          /* :3975 */
              return false;

  This covers `auto` and `always` alike. `test_pattern=always` is a module
  option, not a reason to read a moving window.

- The tick re-checks the same flag inside its `mode_lock` section
  (`:3927`), so a work item that already lost the `cancel_delayed_work_sync()`
  race paints nothing:

      if (sdev->test_pattern_active && sdev->scanout_pitch &&
          !READ_ONCE(sdev->crc_enabled)) {

`sm750_crc_disable()` clears nothing about the card: it stays off until the
next `sm750_pipe_enable()`, which is the only place that decides to paint.
`sm750_crc_suspend()` keeps `crc_enabled`, so a suspend/resume of the source
does not let the card back in mid-session.

3. R2 - ownership, not emptiness, decides the paint
---------------------------------------------------

`test_pattern_fresh` is gone: the field, the set in `sm750_pipe_enable()`, the
skip branch and its comment in `sm750_pipe_update()`, and the clear in
`sm750_test_pattern_cancel()`. `grep -c test_pattern_fresh src/sm750_drm.c`
returns 0. No equivalent one-shot was reintroduced: any such flag would again
have to guess which commit it belongs to, and the ownership test needs no guess.

The paint condition is now, in full:

      if (sm750_test_pattern_should_paint(sdev, blank))           /* :4096 */

with

      return !READ_ONCE(sdev->drm.master) && blank;               /* :3987 */

A userspace DRM master is producing frames by definition, so a black frame from
one - a desktop, a screensaver, a paused video, the CRC harness' own black
buffer - is a picture and is never painted over. The in-kernel fbdev client
never becomes a master, so the `KD_GRAPHICS` case the card exists for still gets
it. `sm750_pipe_update()` now stops the card as its first test-card action
(`:4194`) and reaches its only `goto event` (`:4202`) afterwards.

The other guards are unchanged and still evaluated in the same order: no line
buffer or no circle table, a softscaled window, width < 320 or height < 200, a
pitch smaller than the row or larger than the probe-time line buffer, and a
frame that does not fit the VRAM left after the scanout offset.

The five controls added here, and the defect each one catches:

| control | planted defect | what it would cost |
| --- | --- | --- |
| crc_source_ignored | `should_paint()` loses its `crc_enabled` refusal | the card paints into a window a CRC source is reading: the RCA failure returns |
| crc_arm_keeps_card | `sm750_crc_enable()` no longer cancels | a paint or a queued tick survives arming, so the first CRC entry is torn |
| tick_ignores_crc | the tick drops its `!crc_enabled` re-check | a work item that lost the cancel race paints under the armed source |
| one_shot_upload_skip | a `goto event` inserted before the cancel | the client's first frame is swallowed and the rotation keeps running: exactly A36 |
| black_master_frame | the condition becomes `return blank;` | a desktop, screensaver or CRC harness black frame is painted over |

8. NOT YET OBSERVED ON THE PANEL
--------------------------------

This session has no access to the panel, cannot change the VT and cannot load
the module. Nothing in this file was seen on a monitor.

What is established by the RCA: the pre-fix card made
`tests/check-scanout-crc.sh` fail with three distinct CRCs over twelve static
frames, and the mechanism (a 256-byte read straddling a rotating repaint) is
understood line by line.

What is not established, and needs one root session:

1. Arm the CRC source and confirm the card never appears:

       sudo insmod src/sm750hdmidrm.ko test_pattern=auto
       sudo sh -c 'echo 1 > /sys/kernel/debug/dri/0/crc/control'   # or the harness
       sudo dmesg | grep -c "painted a test card"                  # 0 while armed
       sudo ./tests/check-scanout-crc.sh                           # expected exit 0

2. Disable the CRC source and confirm the card and the disc return on the next
   enable (a module reload on the `KD_GRAPHICS` VT):

       sudo sh -c 'echo 0 > /sys/kernel/debug/dri/0/crc/control'
       sudo modprobe -r sm750hdmidrm && sudo insmod src/sm750hdmidrm.ko
       sudo dmesg | grep "painted a test card"                     # exactly one line

3. Confirm a real client is never painted over: attach a userspace master and
   draw an all-black frame. No `painted a test card` line may appear, and the
   CRC harness must still be able to run its black-buffer test.

4. Confirm the ordering under load: arm the CRC while the disc is moving and
   check that the first CRC entry already matches the second.

The unclosed RCA item - which fbdev-client path triggered the 22:13:39 re-enable
- is root-only as well and is not addressed here.
