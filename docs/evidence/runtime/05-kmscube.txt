======================================================================
TOOLING ROOT CAUSE FOUND FIRST: kmscube EXITS IMMEDIATELY ON STDIN EOF
======================================================================
kmscube polls stdin for the user-interrupt key. When stdin is /dev/null, read()
returns EOF at once, kmscube treats that as "user interrupted!" and exits 0 BEFORE it
prints its frame counter. Earlier runs therefore exited 0 in ~2.8 s with no frame line
and looked like a hang or a silent failure.

  Reproduced:
    kmscube -D /dev/dri/card0 -c 120   (stdin = /dev/null)  -> exit 0
      stdout ends:  ===================================
                    user interrupted!
      no "Rendered ... frames" line

  Fix used for every real run in this file (stdin held open):
    tail -f /dev/null | kmscube -D /dev/dri/card0 -c N

This was a tooling gap, NOT a driver defect. It is recorded here because the earlier
GAP entry for S5 was caused by it.

  strace of a kmscube run shows the real KMS ioctls succeeding on card0:
    DRM_IOCTL_MODE_GETRESOURCES   = 0
    DRM_IOCTL_MODE_GETCONNECTOR   = 0
    DRM_IOCTL_MODE_GETENCODER     = 0
    DRM_IOCTL_MODE_CREATE_DUMB    = 0
    DRM_IOCTL_MODE_MAP_DUMB       = 0
    DRM_IOCTL_MODE_ADDFB2         = 0
    DRM_IOCTL_MODE_SETCRTC        = 0
    DRM_IOCTL_MODE_PAGE_FLIP      = 0
    failing syscalls             : none
  So kmscube really programs crtc 38 on connector 35 at 1920x1080 through the legacy
  SETCRTC + PAGE_FLIP path and really page-flips.

  Independently confirmed by sampling the CRTC binding from a second, read-only client
  while kmscube rendered (/mega/tmp/sm750/t10/readback_during_kmscube.py):
    crtc 38 fb_id changed from 43 (desktop) to 44 and 42 (kmscube's own buffers),
    position (0,0). After kmscube exited, fb_id returned to 0 then 43.
  Lesson recorded: the first process to open card0 holds DRM master, so a probe must
  open the device AFTER kmscube starts, otherwise kmscube itself fails with
  `failed to set mode: Permission denied` and exit 243.

======================================================================
WHAT COULD NOT BE PROVEN, AND WHY
======================================================================
  Panel-visible pixel content was NOT read back from any client, because:
    - there is no /dev/fb* on this host (CONFIG_FB_DEVICE is not set in
      /boot/config-7.3.4-100.fc43.x86_64, although CONFIG_DRM_FBDEV_EMULATION=y and
      dmesg logs `fb0: sm750hdmidrmdrm frame buffer device`);
    - there is no writeback connector (modetest -c reports 0), so `modetest -o` cannot
      dump a frame - it exits 1 with
      `writeback / dump is only supported in atomic mode`;
    - a non-owning client cannot MAP_DUMB another client's GEM handles: GETFB2 on
      kmscube's fbs 42/44 returned handles=(0,...), and MAP_DUMB failed with
      `[Errno 2] No such file or directory`.
  What IS proven: kmscube starts, creates a GL context, takes over crtc 38, page-flips,
  and reports a steady ~59 fps. A frame count and fps are therefore available; the
  pixels on the panel are not.
