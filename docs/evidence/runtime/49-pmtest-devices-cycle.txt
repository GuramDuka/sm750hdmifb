## 1. Why this run happened

Evidence 48 recorded an armed devices-level cycle that stopped at two Tesla
P100s: `nv_pmops_suspend [nvidia] returns -5`, `last_failed_dev=0000:83:00.0`,
and not a single `sm750 ... pm: ` line in the window. The SM750 sleep path was
therefore unmeasured, and defect A66 stayed `open; measurement pending`.

The owner reopened the route himself: he added
`nvidia.NVreg_PreserveVideoMemoryAllocations=0` to the kernel command line and
rebooted (m10287). That parameter exists precisely to make
nv_pmops_suspend() stop returning -5, at the cost of VRAM save and restore
across real sleep, which this test never exercises because pm_test=devices
does not remove power.

## 6. What this proves

- `sm750_pm_suspend()` and `sm750_pm_resume()` ran inside a real system-sleep
  attempt driven by the kernel's own PM core, not by a synthetic call.
- The device-level suspend and resume completed: both edges logged, both
  counted once, no failure line, and the suspend_stats error counters did not
  move, so no device blamed 0000:01:00.0.
- The device survives the cycle: it re-stages the backbuffer, repaints the
  fallback frame and resumes scanning out, with the connector still connected.

## 7. What this does not prove

- No power was removed: pm_test=devices stops before the point where the
  platform would power down, so VRAM retention, hot-plug on a real wake and
  the SiI9022 link after a real power loss are all outside this measurement.
- This host has no S3 (`ACPI: PM: (supports S0 S4 S5)`, `mem_sleep=[s2idle]`),
  so freeze is the only sleep state it has; a deep-sleep claim is not possible
  here at all.
- VRAM preservation on the two Tesla P100s is deliberately disabled for this
  test (`PreserveVideoMemoryAllocations: 0`), so nothing here says anything
  about CUDA context survival across a real suspend.
- `nvidia-modeset: WARNING: GPU:0: Lost display notification` appeared on
  resume; it belongs to the NVIDIA display GPU 0000:02:00.0, not to the SM750,
  and the session continued.
