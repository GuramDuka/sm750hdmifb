================================================================================
5. THE 330.003 ms GAP - WHAT CAN AND CANNOT BE CONCLUDED
================================================================================

Measured gap: 22252.175107 - 22251.845104 = 330.003 ms. This is the interval from the
last successful `staging enabled` line of the PREVIOUS program to the -110 line of the
next one, i.e. it contains (a) the tail of the previous commit, (b) the client's
teardown and close, (c) the restore commit setup, and (d) the failing program_mode up
to the call that timed out. It is therefore an UPPER BOUND on the failing
program_mode, not its duration.

Fixed costs that any program_mode pays before its first fallible call can fail:

  src/sii902x.c:748   msleep(150) in sii902x_begin_control
                      (comment at :747: "Resolution changes require at least 128 ms
                      with TMDS powered down")                      150.0 ms
  src/sii902x.c:695   usleep_range(1000, 2000) in sii902x_init_control_bus
                                                                    1.0-2.0 ms
  ~20 software-I2C byte transfers, ~0.1-0.2 ms each                  2-4 ms
  ---------------------------------------------------------------------------
  fixed subtotal before the display/mode stage                      ~155 ms

Remaining budget for the failing stage: 330.003 - 155 = ~175 ms.

Every wait that can return -ETIMEDOUT on this path, with its quantum:

  src/ddk750_display.c:26  wait_display_value (display-control bit latch)   100 ms
  src/ddk750_display.c:85/:95 primary_wait_vertical_sync phases            50 ms each
  src/ddk750_mode.c:298    PANEL_DISPLAY_CTRL write-verify (cnt>1000)      ~10 ms
  src/ddk750_swi2c.c:229/:306  SCL/ack loops                                <1 ms
  src/ddk750_hwi2c.c:69    I2C poll (unused: use_hardware_i2c is false)     10 ms
  src/sm750_drm.c:1478     DMA1 shadow-upload completion                    5 ms

Arithmetic outcome:
  - exactly ONE 100 ms wait_display_value timeout fits the ~175 ms budget
    (155 + 100 = 255 ms, leaving ~75 ms for (a)-(c) above - consistent with the
    measured 2.6-2.9 s spacing of ordinary attempts and with a fast client teardown);
  - TWO 100 ms waits do NOT fit: 155 + 200 = 355 ms > 330.003 ms, so no single
    ddk750_set_display_control() call can have burned both of its waits;
  - the 2000 ms receiver wait and the 1000 ms DDC-grant wait do NOT fit, and are
    independently excluded because their log lines are absent;
  - the 10 ms verify loop and the sub-ms I2C loops fit but leave ~165 ms unexplained,
    so they are not sufficient on their own.

Ranked inference (this is inference, not observation):
  R1. ddk750_set_display_control(SM750_DRM_CONTROLLER, false) at
      src/sm750_drm.c:1316, failing on the TIMING-clear wait
      (src/ddk750_display.c:53-62). It is the first fallible call after the 150 ms
      quiesce, it is exactly one 100 ms quantum, and its PREVIOUS wait (PLANE clear,
      src/ddk750_display.c:40-52) deliberately ignores its result - so a single
      failing wait there returns -110 with the arithmetic above.
  R2. ddk750_set_logical_disp_out at src/sm750_drm.c:1346, failing on the first
      enable-side wait (src/ddk750_display.c:40-47, TIMING set) - also one 100 ms
      quantum, but it sits ~10 ms later in the sequence, which fits slightly worse.
  R3. ddk750_set_mode_timing at src/sm750_drm.c:1319, failing in the
      PANEL_DISPLAY_CTRL write-verify loop (src/ddk750_mode.c:285-305). Fits the
      budget but leaves ~165 ms unaccounted.
  R4. ddk750_set_logical_disp_out, PNL_SEQ branch -> sw_panel_power_sequence
      (src/ddk750_display.c:100-131) with a 50 ms VSYNC phase timing out: fits only
      if the preceding display-control waits returned immediately.
  R5. sm750_sii902x_begin_mode at src/sm750_drm.c:1312 failing on the control bus
      (src/sii902x.c:695 "control bus is stuck", or a sw-i2c -ETIMEDOUT from
      src/ddk750_swi2c.c:229). Possible, but that path also logs its own error and
      the log shows none.

Mechanistic note supporting R1/R2 over R3: wait_display_value() only POLLS the
register - it pokes once and then reads for up to 100 ms
(src/ddk750_display.c:12-26), whereas ddk750_set_mode_timing() re-pokes up to 1000
times precisely because, per the code comment at src/ddk750_mode.c:288-296,
"PANEL_DISPLAY_CTRL register seems requiring few writes before a value can be
successfully written in ... The hardware will wait for the next vertical sync to turn
on/off the plane." If a single poke fails to latch (or the bit can only change at a
VSYNC that no longer arrives), a single-poke path times out at 100 ms while the
re-poking path recovers. That is consistent with a rare, state-dependent failure and
with the failure appearing on a restore that follows a program by only 330 ms.

What CANNOT be identified on this build, and why: the return site.
  - sm750_program_mode (src/sm750_drm.c:1271-1351) contains NO logging statement at
    all - no dev_dbg, no drm_dbg, no dev_info (verified by reading the whole function
    and by `grep -rn 'dev_dbg\|drm_dbg' src/*.c`);
  - src/ddk750_display.c, src/ddk750_mode.c, src/ddk750_swi2c.c and
    src/ddk750_hwi2c.c contain no dev_dbg/drm_dbg either; the only debug output in
    the driver is 11 sites in src/sii902x.c (:170, :178, :572, :750, :827, :882,
    :947, :968, :998, :1020, :1116) and 3 sites in src/sm750_drm.c (:818, :998,
    :1007) - none of them on the program_mode path;
  - dynamic debug is root-only on this host, so even the existing sites could not be
    switched on from the unprivileged account used here;
  - the 0.5.9 module has no debugfs `regs` file, so PANEL_DISPLAY_CTRL and
    PANEL_PLL_CTRL could not be sampled before/after the failing commit.
Therefore the single unidentifiable call is: whichever of the five fallible calls in
sm750_program_mode returned -110. Everything else in the cascade is established.

================================================================================
7. IS THE REFCOUNT UNDERFLOW THE SAME DEFECT?
================================================================================

Same root cause chain, separate observable, and NOT reproduced.

  - Both the WARN at 8523 and the underflow at 8586 happen on the same path:
    drm_release -> drm_client_dev_restore -> drm_fbdev_client_restore ->
    drm_client_modeset_commit_atomic -> (a failed or dependent commit) -> cleanup.
  - The underflow is a put on an already-zero refcount (RSI=3 = REFCOUNT_SUB_UAF) in
    __drm_atomic_helper_plane_destroy_state, reached from
    drm_atomic_commit_default_clear -> __drm_atomic_commit_free, i.e. while core
    destroys the state of a commit that never completed. A commit can only be in that
    condition because the enable it carried failed - the same -110 that produced the
    WARN - and the fail label left the CRTC's vblank event unconsumed and vblank
    accounting off (src/sm750_drm.c:3105-3117).
  - It is NOT the same code location: the underflow is in core DRM cleanup, not in a
    driver function, and the driver does not touch a plane state's refcount anywhere
    in the file (`grep -n refcount src/sm750_drm.c` returns nothing).
  - It did not recur in the reproduction: the 205-attempt matrix produced one -110 and
    three timeout cascades, but no refcount line. The original's underflow arrived
    62.4 s after the -110, in a different process, after three 10 s stalls, so it needs
    a longer window and an additional client action (a modetest close) than the
    reproduction provided in its 60 s watch.
Conclusion: one defect family, two severities. The driver-side defect (A27) is the
fail path that leaves an inline commit inconsistent; the underflow is its worst-known
consequence and is recorded as part of the same row, flagged as observed-once and not
reproduced. Treating it as a fully separate defect would claim a core-DRM bug that was
not demonstrated.

8. WHAT WOULD SETTLE THE OPEN QUESTIONS
================================================================================

8.1 Identify the failing call (removes R1-R5 ambiguity). Needs a source change; do it
    in a debug build only:
    - In sm750_program_mode (src/sm750_drm.c:1271) add one drm_dbg_kms after each
      fallible call, printing the stage name and ret:
        after :1315  (sii902x_begin_mode)      "stage=begin ret=%d"
        after :1318  (ddk750_set_display_control false) "stage=off ret=%d"
        after :1321  (ddk750_set_mode_timing)  "stage=timing ret=%d"
        after :1348  (ddk750_set_logical_disp_out) "stage=out ret=%d"
        before :1349 "stage=link"
      Four lines total; drm.debug=0x4 (or
      `echo 'module sm750hdmidrm +p' > /sys/kernel/debug/dynamic_debug/control`) then
      names the exact call in one hit.
    - Equally cheap and more precise: change wait_display_value()
      (src/ddk750_display.c:12-26) to log `reg`, the expected and the read-back value
      on the -ETIMEDOUT branch, and primary_wait_vertical_sync()
      (src/ddk750_display.c:68-97) to log which of its two phases timed out plus the
      SYSTEM_CTRL value. That converts R1-R4 into a single certain answer and also
      says whether the bit never latched (read-back wrong) or the VSYNC never came.

8.2 Confirm the hardware state (no source change, 0.6.0 only). The 0.6.0 build exposes
    /sys/kernel/debug/dri/0/regs (src/sm750_drm.c:3343-3344, table at :3282), read as
    root. Sampling it before the failing commit and immediately after the -110 shows:
      - PANEL_DISPLAY_CTRL: bit 8 TIMING and bit 2 PLANE - if TIMING is still set
        after the disable, the disable-side wait (R1) is confirmed; if TIMING is clear
        but PLANE is not, it is the enable-side wait (R2);
      - PANEL_PLL_CTRL: PLL_CTRL_POWER - a powered-down PLL makes
        primary_wait_vertical_sync() return 0 early, which discriminates R4 from R1/R2;
      - PANEL_CURRENT_LINE sampled twice ~20 ms apart: a frozen counter proves the
        raster is not scanning, which is the physical precondition for a 100 ms
        latch timeout;
      - PANEL_HORIZONTAL_TOTAL/PANEL_VERTICAL_TOTAL: whether the previous mode
        (1024x768) or the requested one (1920x1080) is programmed at failure time.
    Closing command: `sudo -n sm750-regs` (the helper) or
    `sudo -n cat /sys/kernel/debug/dri/0/regs` on the 0.6.0 build.

8.3 Confirm the trigger rate on 0.6.0. The 300 ms SIGINT plus modetest shape should be
    re-run at least 40 times on 0.6.0 (the count in Section 6 is a 0.5.9 result). The
    harness is reusable:
      /mega/tmp/sm750/t16/matrix2.sh  (shape L)
      /mega/tmp/sm750/t16/matrix4.sh  (kill-delay sweep)

8.4 Kernel-side confirmation (root, not available here): enable
    `dyndbg` for drm_atomic_helper and ftrace `drm:drm_vblank_event` to see whether the
    vblank event was armed for the failing commit.

9. WHAT REMAINS UNPROVEN
================================================================================

 U1. WHICH call inside sm750_program_mode returned -110. Reason: the function and all
     of ddk750_display.c / ddk750_mode.c have zero debug output, dynamic debug needs
     root, and 0.5.9 has no register debugfs. Ranked candidates in Section 5.
 U2. WHY that call timed out at that moment, i.e. the physical cause (single-poke
     display-control latch vs VSYNC loss vs I2C). Same reason as U1; 8.2 would answer.
 U3. Whether the required trigger is "kill during the first commit" specifically, or
     "any client whose close races with its own recent successful program". The 300 ms
     window hit 1/36 and 100/200/400/1000/2000 ms hit 0/72, which is consistent with a
     narrow window but not proof of one: with n=37 a different 5 % probability shape
     could have been missed.
 U4. The refcount underflow as a repeatable consequence. Observed once, not reproduced
     in 205 attempts; needs a longer watch (>= 70 s) in any future run.
 U5. The exact T10 commands that preceded the original episode (shell history is not
     in the evidence set). The reconstruction in Section 3 is from the kernel log and
     the tier documents, not from the original command lines.
 U6. Behaviour on 0.6.0. Untested by definition: this file is a 0.5.9 result and the
     loaded module is the pre-fix build. Any fix to the fail path must be validated
     with 8.1/8.2/8.3 on 0.6.0.


================================================================================
10. DOES THIS BLOCK A PRODUCTION CLAIM?
================================================================================

Yes, for the driver as it stands. Two reasons, in order of severity:
  1. Any single failed modeset becomes a kernel WARNING plus 30 s of blocked commits
     plus (once observed) a refcount underflow in core DRM cleanup. This is not a
     cosmetic log problem: commits stall for 10 s per atomic object, which is
     user-visible, and a refcount underflow is a use-after-free class warning. The
     driver-side cause is small and local - the `fail:` label at
     src/sm750_drm.c:3105 returns with the CRTC's vblank accounting still off and the
     commit's event unconsumed - so it is cheap to fix, but it is a real defect.
  2. The trigger is a client killed ~300 ms into its first commit followed by a normal
     modeset-and-close; that is an ordinary thing for a session to do (a killed
     fullscreen client, a compositor restart, a crashed demo). The rate is low
     (1/36 in the shape that works) but the consequence is 30 s of stalled commits.
Severity: S3 (functional degradation with a kernel WARN and a use-after-free warning,
recoverable, not a panic). It does not block the panel from being driven - recovery is
automatic and the panel was never left blanked - but it does block a claim that the
driver is production-clean, and it must be fixed or explicitly accepted with the
measured rate before release.
It does NOT block a claim that the 1920x1080 modeset path works: that path succeeded
in every attempt except the single hit, and in every non-kill shape.
