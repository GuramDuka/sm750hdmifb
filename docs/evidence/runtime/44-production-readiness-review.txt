The report carries eleven numbered lead verdicts, each closed with a verdict:
the BUG_ON hit is a comment, the bounded loops are not a defect, the lock
order is `shadow_lock` before `mode_lock`, user input has no writable
attribute outside root, and so on. Six rows survive as defects or risks
(D1-D4, R1, R2). The verdict section reads:

    Overall verdict
    ---------------
    production ready with conditions

    No crash, hang, UAF or leak was confirmed on a path reachable by an
    unprivileged user. The kernel-side bounds, cancellation and lock ordering
    are sound, and the two failure modes that would normally bite a driver
    like this - a dead raster and a dead DDC bus - are bounded and degrade
    instead of hanging. The one unprivileged-reachable defect is D1, an
    undefined hardware scanout read when a client commits a framebuffer
    smaller than the mode; it does not fault the kernel but it is the kind of
    state the driver must not hand to the engine.

    Top three things to fix, in order:
    1. D1: guard the direct scanout path against fb < mode and
       offset + pitch*vdisplay > vram_size (src/sm750_drm.c:3038-3055,
       src/sm750_drm.c:4070-4081). This is the only condition for shipping.
    2. D4 and D3: add the VRAM lower bound before the DMA test carve and the
       0..31 validation for the SiI9022A i2c pins. Both are cheap, both remove
       silent misconfiguration.
    3. D2 and R1: stop reading the charp test_pattern from the commit path
       (cache it at probe), and bound or move the panel power sequence so one
       commit cannot hold mode_lock for about 2.3 s.

## 4. A54 - the panel stays dark when the last client exits

Status `diagnosed`; not raised by either report as a defect, measured while
the review ran. Reproduced on an X session and on three clean `modetest`
self-exits. The state measured after the last client exits:

    PANEL_DISPLAY_CTRL   0x0f010105 -> 0x0f012001
    PANEL_CURRENT_LINE   frozen
    card0-HDMI-A-1/enabled   disabled
    active_crtc          -1

Mechanism, three parts:

1. The DRM core disables the CRTC when the last client removes its
   framebuffer, by design (`atomic_remove_fb`, upstream
   `drivers/gpu/drm/drm_framebuffer.c:1000-1093`). The disable is not the
   defect.
2. The fbdev last-close restore that should re-enable the pipe then never
   issued a commit on about a dozen client exits, although the same function
   works when fbcon calls it (`fb_set_par`, upstream
   `drivers/gpu/drm/drm_fbdev_helper.c:1199-1228`). A manual
   `sudo -n /usr/local/sbin/sm750-console text 2` restored the pipe within
   2 s, so the hardware path is intact.
3. Independently, the VT stayed in `KD_GRAPHICS`. In that mode
   `drivers/tty/vt/vt.c` `do_con_write` drops console output before fbcon
   sees it, so the console does not repaint even with a live pipe.

The stray-fd hypothesis for the missing last-close commit is UNPROVEN: a later
`sm750-headless diagnose` showed module refcount 1 with no holder on card0 or
renderD128.

Workaround in force since 2026-11-26: `tools/sm750-headless.sh` records the VT
before starting a compositor (`vt_record()` at `tools/sm750-headless.sh:359-362`)
and restores a text VT on teardown (`vt_restore()` at `:366-420`), so the
panel repaints automatically. Open question: why the last-close restore never
commits.

## 5. A55 - the CRC reader reported a dead window as a valid one

Status `fixed`. After the last client exits the mode becomes `0x0`, but
`sm750_crc_region_missing()` did not treat a zero mode as missing and
`sdev->scanout_pitch` survived `sm750_pipe_disable()`, so `sm750-crc dump`
printed

    scanout readback, 0x0 pitch 3840

a 0x0 window with a stale pitch. Fixes:

- `sm750_crc_region_missing()` rejects a zero mode before the pitch check
  (`src/sm750_drm.c:3188-3193`).
- `sm750_pipe_disable()` clears `scanout_pitch` and `scanout_frame_size`
  (`src/sm750_drm.c:4394-4395`).
- The shadow upload path refuses a zero-geometry upload rather than
  multiplying a cleared pitch (`src/sm750_drm.c:4305-4311`).
- The debugfs header prints `sm750hdmidrm scanout readback, no active mode`
  for a zero mode (`src/sm750_drm.c:4578-4589`).

Guards: `tests/check-drm-policy.sh` assertions R3, R4 and R5, each with one
property-removing planted control - `plant_crc_zero_mode` (`:524`),
`plant_disable_geometry` (`:533`), `plant_header_zero_mode` (`:542`).

## 7. The architecture verdict

Header of `docs/evidence/review/01-production-readiness-architecture.txt`:

    Reviewer : independent critic-mode review (subagent)
    Date     : 2026-11-26
    Target   : <repo>, src/ (22 files, 11274 lines)
    Method   : source read against the installed 7.3.4-100.fc43.x86_64
               headers and System.map; no code was executed, no kernel or
               device state altered.

Its verdict block:

    VERDICT: production ready with conditions.
    No blocker was found. A plausible blocker was investigated and refuted
    (see "Claims checked and refuted"). Three conditions must be met before
    calling it production ready: make the EDID read non-blocking, decide
    explicitly whether suspend/resume is supported (test it or remove the
    path), and stop reporting a successful commit when the hardware mode set
    failed.

The refuted candidate blocker, quoted from "Claims checked and refuted":

    "Enabling the CRTC with the primary plane disabled causes a NULL
    dereference in sm750_pipe_enable." Not reachable. ... But the simple-pipe
    helper's CRTC atomic_check (drm_simple_kms_crtc_check, System.map:112518)
    rejects an enabled CRTC without an enabled primary plane, and that
    callback lives in drm_crtc_helper_funcs (crtc->helper_private), which the
    driver never overrides [K/S].

The same section refutes the related claim that installing `sm750_crtc_funcs`
(`src/sm750_drm.c:4324-4340`, installed at `:4633`) drops the helper's
`atomic_check`: `atomic_check` is not a `drm_crtc_funcs` member, and the
driver does not assign `helper_private`.

Two of the report's three conditions are closed by this task's fixes: the EDID
read is A57 and the failed-enable report is A56. The third, suspend/resume,
remains open and is recorded as `P1` in the report, not as a ledger row: the
driver's suspend/resume path (`src/sm750_drm.c:5324-5356` in the report's
numbering) has never been exercised.

Note on the wording of the review: the report is a critic-mode review, and its
verdict line is `production ready with conditions`. It does not use the words
"warning" or "revise" anywhere in its 555 lines, so those are not quotes from
it.
