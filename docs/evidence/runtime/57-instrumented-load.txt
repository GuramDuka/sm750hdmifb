3. The eleven GAP-B8 counters, read from the running module
--------------------------------------------------------------------------------

```
$ ls /sys/bus/pci/devices/0000:01:00.0 | grep -c '^b8_'
11
$ for n in b8_mode_attempts b8_mode_failures b8_mode_retries b8_stage_failures \
           b8_i2c_write_timeouts b8_i2c_recoveries b8_ready_expired \
           b8_ddc_grant_timeouts b8_edid_reads b8_edid_failures b8_counters_epoch_s; do
    printf '%s=%s\n' "$n" "$(cat /sys/bus/pci/devices/0000:01:00.0/$n)"; done
b8_mode_attempts=2
b8_mode_failures=0
b8_mode_retries=0
b8_stage_failures=none 0
sii902x_begin_mode 0
ddk750_set_display_control 0
ddk750_set_mode_timing 0
ddk750_set_logical_disp_out 0
sii902x_enable 0
b8_i2c_write_timeouts=0
b8_i2c_recoveries=0
b8_ready_expired=0
b8_ddc_grant_timeouts=0
b8_edid_reads=1
b8_edid_failures=0
b8_counters_epoch_s=3
```

Every attribute exists and is readable. Eight read 0. Three do not, and the
reason is the boot itself, not a wiring error:

* `b8_mode_attempts=2` - the console framebuffer and the automatic test card
  each programmed a mode during probe.
* `b8_edid_reads=1` - the panel EDID was read once at probe.
* `b8_counters_epoch_s=3` - this is not a count but a timestamp:
  `src/sm750_drm.c:5848` sets it to `ktime_get_boottime_seconds()` at probe, so
  3 means the counters began at 3 s after boot.

`b8_stage_failures` is a multi-line attribute: the first line is the last
failing stage name or `none`, then one line per mode stage with its count. The
plan's criterion for this attribute was "exists and reads 0"; the literal first
line here is `none 0` (no stage has failed, zero failures) and all five stage
lines read 0. That is the intended state; the wording, not the value, is what
differs from "0".

The counters are device attributes, so they are per card, and the PCI address
`0000:01:00.0` is the only sm750 device on this host.

4. A65 marks: parameter present, capture still owner-gated
--------------------------------------------------------------------------------

```
$ cat /sys/module/sm750hdmidrm/parameters/a65_trace
N
$ (sudo -n dmesg) | grep -c 'A65:'
0
```

The parameter exists in the running module (it did not in 0.6.10 before this
release only by accident of what was loaded; 0.6.10 did have it - what 0.6.10
lacks is the nineteen-mark partition and the counters). Zero `A65:` lines is
expected: `a65_mark()` prints only when `a65_trace` is true
(`src/sm750_drm.c:325-329`), and the parameter was never written since boot, so
no teardown has been traced on this load.

Enabling the trace does NOT need a reload: the parameter is mode 0644 and
writable at runtime. The remaining step is a hot-remove attempt with the trace
on, which is the owner-gated A65 work (T8), and it is not part of T7:

```
# owner, as root (no allowlisted helper writes module parameters):
echo 1 > /sys/module/sm750hdmidrm/parameters/a65_trace
# then the T8 remove route, with the owner present and the single reboot granted;
# capture:  sudo -n sm750-hang capture <dir>   and the A65: lines from dmesg
```

The nineteen marks are in the running module's source
(`/usr/src/sm750hdmifb-0.6.11/src/sm750_drm.c`, byte-identical to the tree):
remove enter, before/after `poll_fini`, before/after `test_pattern_cancel`,
before/after `vblank_stop`, before/after `atomic_shutdown`, before/after
`drm_dev_unplug`, before `sii902x_shutdown`, `mode_lock acquired`, after
`sii902x_shutdown`, remove exit, plus shadow worker enter, before/after
`async_quiesce`, and after `destroy_workqueue`.

6. What this file does not claim
--------------------------------------------------------------------------------

* It does not claim a hot reload, a hot remove, a suspend cycle, or a mode set
  under load was exercised on 0.6.11. The module was loaded once by the boot and
  has served the console and the test card since.
* It does not claim A65 evidence exists for this release. The nineteen marks are
  in the payload; the trace has not been switched on, and no remove has happened
  since boot. The T4 ordering gate is source-level and is recorded separately
  (`tests/check-a65-trace.sh`); `docs/evidence/a65/02-mark-and-ordering-gate.txt`
  and `docs/evidence/builds/29-a65-ordering-build.log` are absent from this tree,
  so this file does not cite them.
* The counter values are a single snapshot 11 minutes after boot, not a
  monotonicity run. A 24-48 h soak with the counters non-zero is the T6 helper's
  job and is not claimed here.
