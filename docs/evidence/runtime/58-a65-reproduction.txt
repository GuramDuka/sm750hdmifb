What this proves

On this host, this kernel and this module, the T4-ordered teardown completed a
raw `modprobe -r` with fbcon bound and with no userspace holder, reaching
`remove exit` with no block. The mitigation path and the raw path both produced
the same 18-mark sequence in the same order.

What this does not prove

One clean run does not prove the wedge is gone. No stack was captured because
nothing blocked, so C1 (console_sem inside drm_dev_unplug), C2a/C2b (workqueue
and fb_helper flush) and C3 (mode_lock around sii902x shutdown) remain
unexercised as failure modes on this run rather than excluded. The shadow
worker never fired, so the C2b ordering was not tested with the worker busy.
The control and the raw run differ in exactly one variable - the helper's
fbcon detach and device unbind before unload - and both completed; nothing in
this evidence identifies which of the three candidates, if any, was the
original cause. A wedge that needs concurrency, a busy worker or a holder to
reproduce was not attempted and was not seen.
