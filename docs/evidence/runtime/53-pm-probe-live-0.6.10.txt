--------------------------------------------------------------------------------
1. Why this file exists
--------------------------------------------------------------------------------

Two things were unproven after the 0.6.10 release:

  * that the installed RPM and the DKMS module actually move from 0.6.9 to
    0.6.10 on this host, and
  * that the A67 fix in tools/sm750-pm-probe.sh reports a passing cycle as a
    pass on live hardware, not only in the gate fixtures.

Both are measured below.

4. Reload: 0.6.9 -> 0.6.10 with the console detached
--------------------------------------------------------------------------------

  $ sudo -n /usr/local/sbin/sm750-vt off
  sm750-vt: device unbound, refcnt after the unbind: 0
  sm750-vt: module unloaded
  sm750-vt: device re-bound, /sys/bus/pci/devices/0000:01:00.0/driver ->
            /sys/bus/pci/drivers/sm750hdmidrm
  fbcon:        detached then re-bound to /sys/class/vtconsole/vtcon1, bind=1
  device:       0000:01:00.0 unbound then re-bound to sm750hdmidrm
  reloaded:     0.6.9 -> 0.6.10 (srcversion=6DA22404EEA85B6D6535912 refcnt=1)

This is the same unload path that wedged in A65 on 2026-11-26, and it completed
in under a second. The difference is the order the helper enforces: fbconsole
detached before the unload, which is exactly the guard added after A65.

  $ cat /sys/module/sm750hdmidrm/version
  0.6.10
  $ cat /sys/module/sm750hdmidrm/srcversion
  6DA22404EEA85B6D6535912
  $ cat /sys/module/sm750hdmidrm/refcnt
  0

Style note: the sysfs refcnt reads 0 while sm750-vt reports refcnt=1 during its
own run, because the helper holds a reference for the length of the operation.

5. pm_probe cycle on 0.6.10, read by the fixed helper
--------------------------------------------------------------------------------

  $ sudo -n /usr/local/sbin/sm750-pm-probe cycle
  driver:     0.6.10
  refcnt:     0
  raster:     0x0000007f
  writing cycle to /sys/bus/pci/devices/0000:01:00.0/pm_probe
  raster:     0x00000161
  kernel log:
    Nov 27 19:09:12 deneb kernel: sm750hdmidrm 0000:01:00.0: [drm] pm probe: command cycle
    Nov 27 19:09:13 deneb kernel: sm750hdmidrm 0000:01:00.0: [drm] pm probe: cycle suspend ok, resume ok
  verdict:    pass (callback bodies ran and returned 0; this is not a system sleep)

The raster advanced across the call (0x7f -> 0x161), so the display engine kept
scanning while the callbacks ran, and the helper accepted the combined cycle
line instead of demanding a per-command line it would never see. That is the
A67 fix, observed on hardware rather than in a fixture.

What this does not claim: no PCI config space was saved or restored, the device
never entered D3hot, and no power state changed. The devices-level pm_test cycle
that did run end to end is evidence 49.
