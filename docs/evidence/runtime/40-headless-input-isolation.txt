3. The launching session is the service account, not the owner
---------------------------------------------------------------
```text
$ id -u
1005
$ cat /proc/self/loginuid
1005
$ loginctl list-sessions
     (seat0 listed only for the owner's session; the service account's
      session shows Seat= and Remote=yes)
```

`coder` holds no seat, and libseat 0.9.x then has no manager to ask. Under
`LIBSEAT_BACKEND=noop` - the only usable backend here, since seatd is not
installed (`/usr/bin/seatd` and `/usr/sbin/seatd` absent, no `seatd*` unit, no
`/run/seatd.sock`) while `libseat.so.1` is present at /usr/lib64/libseat.so.1 -
libseat opens the evdev node itself. Nothing in that path can refuse the open,
which is why the grab reached the owner's hardware.


4. Why no compositor flag can fix this
--------------------------------------
weston 14.0.2 `--help` places `--no-input  Dont create input devices` under
`Options for x11:` only. The DRM backend accepts exactly `--seat`,
`--drm-device`, `--additional-devices`, `--use-pixman`, `--current-mode` and
`--continue-without-input`. `--continue-without-input` means "start even when
zero input devices appear"; it does not stop weston from opening devices that
do appear, and the incident run passed it.

cage 0.2.x has no input option at all: `-d`, `-m extend|last`, `-s`, `-v`, `-h`.
It is wlroots-based, so it does honour `WLR_LIBINPUT_NO_DEVICES=1`, which the
helper still exports for that reason; weston does not read that variable.

The conclusion is that the guard cannot be an argument. It has to be the
absence of the device nodes.


5. The fix: a private mount namespace with an empty /dev/input
---------------------------------------------------------------
`tools/sm750-headless.sh:244-253`:

```sh
isolate() {
	exec "$UNSHARE" --mount --propagation private /bin/sh -c '
		"$1" -t tmpfs -o size=1M,mode=0755 tmpfs /dev/input || {
			echo "sm750-headless: cannot seal /dev/input in the private namespace" >&2
			exit 1
		}
		shift
		exec "$@"
	' sm750-headless "$MOUNT" "$@"
}
```

Both compositor arms call it (`:258` weston, `:264` cage); kmscube keeps its
plain exec. `$UNSHARE` is `/usr/bin/unshare` and `$MOUNT` is `/usr/bin/mount`,
both checked with `[ -x ]` before any compositor starts (`:85-114`), and the
run exits 1 with "refusing to start a compositor without input isolation" if
either is missing - the isolation is never silently skipped.

`--propagation private` is required. `/dev` on this host is a shared mount:

```text
$ awk '$5=="/dev"{print $7}' /proc/self/mountinfo
shared:2
$ findmnt -no PROPAGATION /dev
shared
```

A mount created in a namespace that kept shared propagation can propagate to
the host; making the namespace private first removes that path. The mount lives
only in the child namespace, so the host is not modified at all.

The intermediate `/bin/sh` is replaced by the compositor with `exec`, so the
compositor keeps the pid the EXIT trap sends TERM then KILL to; the cleanup
semantics are unchanged.


6. Measurements taken, and what is NOT YET OBSERVED
---------------------------------------------------
Measured 2026-11-26 as `coder`, without starting any compositor:

```text
$ /usr/bin/unshare -rm --propagation private /bin/sh -c \
    'mount -t tmpfs -o size=1M,mode=0755 tmpfs /dev/input && \
     ls -A /dev/input && echo EMPTY-OK'
EMPTY-OK
rc=0

$ findmnt -o TARGET,PROPAGATION /dev      # inside the namespace
TARGET PROPAGATION
/dev   private

# after the run, on the host:
$ ls -A /dev/input | wc -l
18
$ ls /dev/input/event* | wc -l
13
$ findmnt -no PROPAGATION /dev
shared
```

`/usr/bin/unshare` is not on the sudoers allowlist, so the user-requested
`sudo -n /usr/bin/unshare --mount ...` form cannot run on this host:

```text
$ sudo -n /usr/bin/unshare --mount sh -c 'true'
<localised "a password is required" message>
rc=1
```

The message is localised on this host and is not ASCII, so it is not
reproduced verbatim here; this repository is ASCII only. The exit status and
the fact that the command required a password are the load-bearing part.

The equivalent proof above therefore runs under `unshare -rm` as the service
account. Inside the real helper the same `unshare` runs as root, where the `-r`
mapping is unnecessary.

The helper's `isolate()` was additionally exercised end to end without a
compositor: `$UNSHARE` was pointed at a wrapper that runs `/usr/bin/unshare -r`,
and `isolate /bin/sh -c '...'` reported `child-entries=0`, `child-pid` equal to
the parent pid (proving the exec replaced the shell), a `tmpfs` mount at
`/dev/input` inside the namespace, and exit 0. The host afterwards still had 18
entries / 13 event nodes and `shared` propagation on `/dev`.

NOT YET OBSERVED

- The isolated run has not been executed on the host. `/usr/local/sbin/sm750-headless`
  is still the 9223-byte, sha256
  `137c665b7f60c17a95a6bdcd7948fb7064239eb62a6a108932e60315ce80913c` revision
  without this code; the owner must refresh it first with
  `sudo install -m 0755 -o root -g root tools/sm750-headless.sh /usr/local/sbin/sm750-headless`
  from the repository root. Running it is the owner's action, not this task's:
  a compositor run is exactly what caused the incident and the owner's session
  is live on this machine.
- No weston or cage run has been made with the namespace in place, so "weston
  logs zero `device is a keyboard` lines and zero `libinput: configuring

- Installed-copy hashes after a refresh are unknown by construction; the

- The residual case is out of scope and unchanged: a compositor started on a
  real VT under logind is supposed to take that seat's devices.
