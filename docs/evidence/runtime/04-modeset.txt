WHAT THE MODESET ACTUALLY DID - PROOF FROM modetest -p AND FROM dmesg
======================================================================

1. modetest -p cannot see the alternate mode while the -s process is still alive in
   this single-shot form, because the mode is reverted when the modetest process exits
   (DRM master drop / fbdev restore). Sampling modetest -p in a tight loop DURING the
   set captured the transient:
       (1920x1080)  ->  (0x0)  ->  (1920x1080)
   A 12 s idle control run produced a dmesg delta of 0 lines, so the revert is tied to
   process exit, not spontaneous.

2. dmesg proves the alternate mode really is programmed and then reverted. From
   /mega/tmp/sm750/t10/attrib.log (single-command runs with exact dmesg deltas):
     A. modetest -s 35@38:1920x1080 (re-apply active mode)
        exit=0, dmesg lines added: 2
          [14855.866365] SiI9024A receiver not ready after 2000 ms: HPD=1 RSEN=0 status=04; enabling for compatibility
          [14855.870350] [drm] full-frame backbuffer staging enabled (4147200 bytes per buffer)
     B. modetest -s 35@38:1024x768-60 (alternate mode)
        exit=0, dmesg lines added: 4
          [14870.761127] SiI9024A receiver not ready after 2000 ms: HPD=1 RSEN=0 status=04; enabling for compatibility
          [14870.765097] [drm] full-frame backbuffer staging enabled (1572864 bytes per buffer)
          [14873.337095] SiI9024A receiver not ready after 2000 ms: HPD=1 RSEN=0 status=04; enabling for compatibility
          [14873.341075] [drm] full-frame backbuffer staging enabled (4147200 bytes per buffer)
        1572864 = 1024*768*2 (the alternate mode was staged) and 4147200 = 1920*1080*2
        (the original mode was staged again 2.576 s later, on process exit).
        This is the cleanest single proof that the alternate mode is really programmed
        and then automatically reverted.
   Entire-boot histogram of the staging line:
       55x "(4147200 bytes" (1920x1080x2), 12x "(1572864 bytes" (1024x768x2),
        1x "(1843200 bytes" (1280x720x2).
   The 1280x720-60 alternate mode behaves identically (1843200 = 1280*720*2, then
   4147200 on exit).

3. Repetition: the re-apply-active-mode step was repeated 6x and the alternate-mode
   step 6x, every one exit 0 with empty stderr; the same staging-pair signature was
   observed each time.

======================================================================
TOOLING CAVEAT - EXIT CODE 0 IS NOT PROOF OF A SUCCESSFUL MODESET
======================================================================
modetest exits 0 even when the modeset fails. Observed verbatim:
    /usr/bin/modetest -s 35@38:9999x9999        -> exit=0
      stderr: failed to find mode "9999x9999" for connector 35
      stderr: failed to create dumb buffer: Invalid argument
This was checked explicitly for the acceptance criterion "every command, exit code".
Therefore the exit codes above are reported for completeness only; the evidence that a
modeset happened is the dmesg staging-byte change plus the modetest -p transient, not
the exit code.

ATOMIC PATH IS A SILENT NO-OP ON THIS STACK
    /usr/bin/modetest -a -s 35@38:1024x768-60  -> exit=0 but prints nothing, changes
    nothing: crtc stayed 38/43 1920x1080 and the dmesg delta was 0 lines.
    /usr/bin/modetest -a -s 35@38:1920x1080    -> exit=0, no-op.
Only the legacy `-s` path (which the driver's drm_atomic_helper_commit serves) actually
reprograms the CRTC from this tool. Recorded as observed behaviour of the stale 0.5.9
build plus drm-utils 2.4.134; not interpreted further.

TRANSIENT FAILURE ONCE OBSERVED (recorded, not interpreted as a driver defect)
  One backgrounded modetest run racing the concurrent modetest -p prober printed
      failed to set mode: Permission denied
  on stderr while still exiting 0. Two DRM clients cannot both hold master, so this is
  a client-side arbitration race in the test harness, not a driver failure.
