===========================================================
Plan: docs/plan/20261127-sm750-strict-production/plan.yaml, task T8
Nature: phase A of a two-phase job. Phase A is the MITIGATION CONTROL: the
        helper-driven reload (sudo -n /usr/local/sbin/sm750-vt off, then on)
        run once with a65_trace armed, before the single unmitigated attempt.
        Phase A does not attempt the wedge. It proves the trace is live and
        records the mark sequence and count on the safe path, so phase B has a
        baseline to differ from.

Absent expected mark: 'A65: shadow worker enter'. It is present in the binary
(src/sm750_drm.c:2727) but did not fire during this reload: the mark prints only
when the shadow worker actually runs, and no shadow damage was queued inside the
teardown window. The last trace-armed worker entry in this boot was at 12:48:39,
before the attempt-2 baseline (see 01b-before.txt, tail).

Correction to the brief's expectation, stated plainly and without padding: the
expected count of sixteen (and the premise that three of the nineteen belong to
the unmitigated raw path) does not match the installed 0.6.11. The three
sm750_destroy_shadow_workqueue marks (before async_quiesce, after
async_quiesce, after destroy_workqueue) DID appear on the helper path, because
T4 moved that teardown from a devres action into .remove. The count on the
helper path is therefore 18 of 19, not 16. The 0.6.10 evidence 54 recorded
sixteen only because that build had not yet added the T4 marks (before
sii902x_shutdown, mode_lock acquired) or the worker-entry mark.

Ordering observation: the sequence shows the T4 contract order, i.e. producers
stopped (poll_fini, test_pattern_cancel, vblank_stop) and the pipeline shut down
(atomic_shutdown) BEFORE the shadow queue was destroyed and before unplug, with
unplug before the SiI902x power-down. This differs from the 0.6.10 order in
evidence 54, where 'before unplug' preceded test_pattern_cancel. No mark appears
twice and none out of source order.

set to Y before this control was consumed by the reload: the freshly loaded
0.6.11 reads a65_trace=N. Any further trace capture needs a new root write of 1
to /sys/module/sm750hdmidrm/parameters/a65_trace after the load.
