SM750 card cannot be read as uid 1005. The file this record would contain is
/sys/kernel/debug/dri/<N>/crtc-0/crc/source, plus the enabled state written
through crc/control.

Why no workaround exists on this host
-------------------------------------
The sudoers allowlist holds sm750-regs, sm750-lspci, sm750-vbios-dump, dmesg,
journalctl -k, dkms, depmod, modprobe -r sm750hdmidrm, dnf for the package and
dmidecode (docs/ROOT-ACTIONS.md). None of them reads or mounts debugfs, and no
unprivileged path to /sys/kernel/debug/dri exists, so the source list cannot be
captured here.

Update (T26 follow-up, 2026-11-19): the source list now comes from the driver.
The CRTC is created by drm_simple_display_pipe_init() with the simple-pipe
funcs; sm750_crtc_funcs is swapped in at src/sm750_drm.c:4029, after DRM has
already registered the CRTC, and
drm_debugfs_crtc_crc_add() is not exported, so DRM never creates crtc-N/crc/.
The driver therefore hosts crc/source, crc/control and crc/data itself from
sm750_crtc_late_register() and again from sm750_regs_debugfs_add(), which also
covers kernels that create the CRTC directory before the debugfs hook. Userspace
sees the documented uapi: crc/source reads "scanout", crc/control reads "none"
or "scanout" and accepts none/auto/scanout, and crc/data first emits the value
count ("1") once per open and then one "%u %08x" line per frame (decimal vblank
count, hex crc, no 0x prefix). Blocked on root for the
observation: docs/evidence/scanout/06-crc-debugfs-runtime.txt.
