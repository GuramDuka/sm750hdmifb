## 3. Why 49152 bytes is the whole image

The ROM header and the PCI data structure agree on the length, and the image
satisfies the VGA checksum at that length:

- header byte at 0x02 is 0x60 = 96; 96 * 512 = 49152
- PCIR image-length field at 0x2c is 0x0060 = 96 units of 512 = 49152
- the file is exactly 49152 bytes, so file length == declared length
- sum of all 49152 bytes modulo 256 = 0 (a valid VGA option ROM checksum)
- bytes 0x815d..0xbfff are a pure 0xcc padding run, 16035 bytes, and there is
  no non-0xcc byte beyond 0x815c: the code region ends and the image is padded
  to its declared size
- there is exactly one "PCIR" occurrence in the image, at 0x1c; there is no
  second image concatenated after it

So the image is complete at 48 KiB. The 64 KiB figure the task text and the
helper assume is wrong for this device: the ROM BAR aperture is 64 KiB
(`Expansion ROM at c7400000 [disabled] [size=64K]`), but the image the BAR
returns is 48 KiB. Reading past 48 KiB would only read padding, and the two
runs both stop where the device stops.

CONSEQUENCE FOR THE HELPER (not changed by this task): the EXPECT constant in
/usr/local/sbin/sm750-vbios-dump should become 49152. This task does not edit
the helper: it is a root-owned host path, the sudo grant is on the path, and a
future edit needs the host owner again. Until then every run of the helper
exits 2 on a good capture, which is a false alarm, not a defect.

## 5. PCI data structure (PCIR)

Offset 0x18 holds a 2-byte little-endian pointer, 0x001c, to the PCI data
structure. "PCIR" itself is at 0x1c, not at 0x18. Fields as read from the
bytes above:

| Offset | Bytes     | Field             | Value                                   |
| ------ | --------- | ----------------- | --------------------------------------- |
| 0x00   | 55 aa     | signature         | 0xaa55 (valid x86 option ROM)           |
| 0x02   | 60        | size / 512        | 96 -> 49152 bytes                       |
| 0x03   | e9 50 12  | entry jump        | near jmp to 0xc1256                     |
| 0x18   | 1c 00     | PCIR pointer      | 0x001c                                  |
| 0x1c   | 50 43 49 52 | signature       | "PCIR"                                  |
| 0x20   | 6f 12     | vendor ID         | 0x126f (Silicon Motion)                 |
| 0x22   | 50 07     | device ID         | 0x0750 (SM750)                          |
| 0x24   | 00 00     | VPD pointer       | 0x0000 (no VPD)                         |
| 0x26   | 18 00     | structure length  | 0x0018 = 24 bytes                       |
| 0x28   | 00        | structure revision| 0x00                                    |
| 0x29   | 00 00 03  | class code        | 0x030000, display controller            |
| 0x2c   | 60 00     | image length      | 0x0060 = 96 units of 512 = 49152 bytes  |
| 0x2e   | 00 00     | code revision     | 0x0000                                  |
| 0x30   | 00        | code type         | 0x00, x86                               |
| 0x31   | 80        | indicator         | 0x80, last image in the ROM             |
| 0x32   | 00 00     | runtime length    | 0x0000                                  |
| 0x34   | 6b        | checksum byte     | 0x6b                                    |

The vendor/device pair matches the PCI configuration space capture
(`docs/evidence/baseline/07-pci-config-space.txt`, `01-lspci.txt`): 126f:0750.
The indicator 0x80 (last image) is consistent with the single "PCIR" occurrence
found in the image.

UNDETERMINED: the PCIR checksum. Under the usual convention the checksum is the
last byte of the structure and the sum of the whole structure including it is 0
modulo 256. Both readings fail here: if the structure is 0x1c..0x33 (24 bytes,
the value in the length field) the checksum byte is 0x34 = 0x6b and the 25-byte
sum is 108; if the checksum is the last byte of the 24 bytes, it is 0x33 = 0x00
and the 24-byte sum is 1. Spans from 0x00 also fail. So the PCIR checksum does
not validate under either convention, and the intended span is not determinable
from the image alone. It is recorded as observed, not guessed at. This does not
affect the whole-image checksum, which is valid (0 modulo 256).

The byte at 0x35 is 0x09 and is not part of the 24-byte structure; it sits
between the structure and the "Version" text at 0x36. Its meaning is
undetermined and no interpretation is attached to it.

## 6. VESA BIOS extension structure

At 0x7f the image carries a VBE signature block. Raw bytes 0x7f..0xa0:

    5645534100025b0000c000000000ac7a00c0534d373530000d0a436f7079726967

| Offset | Bytes     | Field       | Value                              |
| ------ | --------- | ----------- | ---------------------------------- |
| 0x7f   | 56 45 53 41 | signature | "VESA"                             |
| 0x83   | 00 02     | version     | 0x0200 (VBE 2.0)                   |
| 0x85   | 5b 00 00 c0 | OEM string | far 0xc000:0x005b -> file 0x005b   |
| 0x89   | 00 00 00 00 | capabilities | 0x00000000                      |
| 0x8d   | ac 7a 00 c0 | mode list  | far 0xc000:0x7aac -> file 0x7aac   |

The OEM string far pointer resolves correctly and lands on the banner quoted
in section 7, so the pointer convention (offset word first, segment second) is
confirmed by a hit.

The header stops at 0x90: the ASCII string table begins at 0x91 with "SM750",
which is exactly where a full VBE 2.0 block would carry the total-memory word.
The total-memory field is therefore not populated in this image; the bytes
there are text, not a count. Reading them as a number yields 19795, which is
an artefact of the overlap and is not reported as a memory size.

The mode-list pointer resolves to file offset 0x7aac, whose first words are
0x7adf, 0x7ad7, 0x7acf, 0x7ac9. These are not plausible VBE mode numbers (a
mode list holds 0x0NNN values terminated by 0xffff), and no 0xffff terminator
appears in that region. So the mode list does not decode as a VBE mode table.

UNDETERMINED: the mode-list contents and the total-memory field. Both are
recorded as read, with no interpretation attached. The VBE block is present
and its version and OEM string are usable; its deeper fields are not.
