`/mega/tmp/sm750/<task>/`; `dnf download --destdir /mega/tmp/sm750/<task>` is
the expected form. Repository deliverables (`docs/ENVIRONMENT.md`,

Two pre-existing `$HOME` entries are not T3 scratch but are noted so packaging
tasks do not add to them: `~/.rpmmacros` and the empty
`~/rpmbuild/` skeleton were created by `rpmdev-setuptree` at 18:59,
before this task; a packaging task should redirect `%_topdir` under
`/mega/tmp/sm750/` instead of filling that skeleton. The `check-vblank`
compile runs through `/usr/lib64/ccache/cc`, so it deposits objects in the
user ccache (`~/.cache/ccache`); that is a tool cache, not a
scratch file, and `CCACHE_DIR` can be pointed at `/mega/tmp/sm750/t3/ccache`
to keep it out of `$HOME` entirely. This paragraph names those paths with `~/`
on purpose: the file ships in the source archive, and
`tests/audit-release.sh:89-95` rejects a local absolute home path there
(defect A29).

## 4. Rootless libdrm procedure (verbatim)

No package is installed and no root operation is used. The RPM payloads are
unpacked into `/mega/tmp/sm750` and consumed through `PKG_CONFIG_PATH`.

```sh
mkdir -p /mega/tmp/sm750/t3/libdrm
cd /mega/tmp/sm750/t3/libdrm
dnf download libdrm libdrm-devel
for r in *.rpm; do rpm2cpio "$r" | cpio -idm; done

export PKG_CONFIG_PATH=/mega/tmp/sm750/t3/libdrm/usr/lib64/pkgconfig
export PKG_CONFIG_SYSROOT_DIR=/mega/tmp/sm750/t3/libdrm
export LD_LIBRARY_PATH=/mega/tmp/sm750/t3/libdrm/usr/lib64
```

The equivalent one-liner form, preferred when the directory is not already
current, is `dnf download --destdir /mega/tmp/sm750/t3/libdrm libdrm
libdrm-devel` followed by the same `rpm2cpio | cpio -idm` loop. Nothing is
left under `/tmp/opencode`: `ls /tmp/opencode | grep '^t3'` returns no lines.

### 5.1 Device access

The card registers no render node. `/dev/dri/by-path/` contains
`pci-0000:01:00.0-card -> ../card0` and nothing else for `01:00.0`; the
`renderD128`, `renderD129` and `renderD130` nodes belong to `02:00.0`,
`83:00.0` and `84:00.0` (NVIDIA). A render node is not a KMS device in any
case, so it cannot enumerate connectors or modeset.

The DRM minor in the debugfs path is the `cardN` suffix and is assigned in
probe order, so it must be resolved rather than assumed to be `0`:

```sh
card=$(readlink -f /dev/dri/by-path/pci-0000:01:00.0-card)   # -> /dev/dri/card0
minor=${card##*/card}
```

Update (T9, 2026-11-18 09:31): the node is now open to this account. The udev
rule was installed by the user and re-applies the ACL at every probe;
`getfacl /dev/dri/by-path/pci-0000:01:00.0-card` reports `user::rw-`,
`user:duka:rw-`, `user:coder:rw-`, `group::rw-`, `mask::rw-`, `other::---`.
`modetest -c` therefore succeeds after skipping the other cards:

```
trying to open device '/dev/dri/card3'... failed
trying to open device '/dev/dri/card2'... failed
trying to open device '/dev/dri/card1'... failed
trying to open device '/dev/dri/card0'... done
opened device `SM750G10 SiI9024A HDMI DRM shadow driver` on driver `sm750hdmidrm` (version 0.1.0 at 0)
```

The three failures are the other DRM cards in `cardN` scan order, not a
permission error. `version 0.1.0` is the stale installed module; 0.6.0 fixes
the reported version but needs a module reload (root) to be visible live.

The three mechanisms and their state:

| Mechanism | Path | State 2026-11-18 |
| --- | --- | --- |
| udev ACL rule | `/etc/udev/rules.d/99-sm750-coder-acl.rules` | **installed** (`root:root 0644`, 710 B, mtime 09:15). It matches `ACTION` `add` or `change` on `SUBSYSTEM=="drm"`, `KERNEL=="card[0-9]*"`, `SUBSYSTEMS=="pci"`, `ATTRS{vendor}=="0x126f"`, `ATTRS{device}=="0x0750"` and runs `setfacl -m u:coder:rw /dev/$name` |
| One-shot ACL | `sudo setfacl -m u:coder:rw /dev/dri/card0` | not needed; would be lost on the next probe |
| `video` group | `sudo usermod -aG video coder` | not applied; `getent group video` still lists only `cosmic-greeter,duka` |

With the rule in place, `docs/evidence/EVIDENCE-GAPS.md` GAP-B3 is downgraded
from `GAP` to `PARTIAL`: connector and mode enumeration work unprivileged, but
no modeset, framebuffer readback, scanout CRC or external capture has been
performed, so no KMS client result is claimed anywhere in this corpus.

### 5.2 Sudoers allowlist

The installed allowlist is the 0.6.0 file: `/etc/sudoers.d/10-sm750-debug`,
mode `0440 root:root`, 4047 bytes, sha256
`d2141159a99e65ba3c150e20daba915babbe907674a80bfbce1fce598ed35a3b`, installed
by the host owner on 2026-11-18 at 08:37Z. `sudo -n -l` lists **19 NOPASSWD
entries**: 16 for this work plus the three that predate it (`/usr/bin/dmidecode`,
`/usr/local/cuda/bin/ncu`, `/usr/local/cuda/bin/nvprof`). Every `dkms` line and
the `dnf install` path name 0.6.0:

```text
/usr/local/sbin/sm750-regs
/usr/bin/dmesg
/usr/bin/journalctl -k -b --no-pager
/usr/bin/journalctl -k -b -q --no-pager
/usr/local/sbin/sm750-lspci

dkms install -m sm750hdmifb -v 0.6.0
dkms uninstall -m sm750hdmifb -v 0.6.0
dkms build -m sm750hdmifb -v 0.6.0
dkms remove -m sm750hdmifb -v 0.6.0 --all
/usr/bin/depmod -a

/usr/bin/dnf install -y /mega/tmp/sm750/t6/rpmbuild/RPMS/noarch/sm750hdmifb-0.6.0-1.fc43.noarch.rpm
/usr/bin/dnf remove -y sm750hdmifb
```

Design rule: **zero colons in command lines**. sudoers treats `:`, `,`, `=`
and `\` as special inside a command argument, and an earlier installed copy
failed with `syntax error at lines 32:63 and 33:60` because two `lspci` lines
carried unescaped `01:00.0` and `126f:0750`. Anything needing a PCI address or a
vendor:device pair goes through a helper in `/usr/local/sbin` instead. The colon
audit in `docs/evidence/builds/18-sudoers-verify-0.6.0.log` returns `0`, and the
staged file passes `visudo -c -f` both standalone and appended to a copy of the
stock `/etc/sudoers`.

The live file cannot be read by `coder` (`ls /etc/sudoers.d` is denied), so
verification is by `sudo -n -l` content only. `sudo -n visudo -c` and
`sudo -n cat /etc/sudoers.d/10-sm750-debug` are deliberately NOT granted: a
`cat` grant on that path would read every future allowlist, and the staged file
is already parse-checked. Do not add them to close a verification gap.

Three helpers are installed, all `0755 root:root`, all colon-free at the call
site:

| Path | sha256 | Effect |
| --- | --- | --- |
| `/usr/local/sbin/sm750-regs` | `1a345ff074b92d93d17ddf6deabb93bb05b4ff02a029ee3a2de5d70c302ebe60` | resolves the debugfs index from the by-path link, then reads `/sys/kernel/debug/dri/<N>/regs` |
| `/usr/local/sbin/sm750-lspci` | `4b4f555a5f70c369d54196e1b4fa7750d91cb1e1b7fa5938a05d93866968af10` | dumps config space with `lspci -vvv -xxx -s 01:00.0` and `-vvv -d 126f:0750` |
| `/usr/local/sbin/sm750-vbios-dump` | `e2f6f68791ebd3f341ca77cb84169bda8843c1ce192f2e500b51faa01e67f585` (v1) | enables the PCI expansion ROM, copies the image, restores the enable bit through a trap |

The installed `sm750-vbios-dump` is the **v1 body and is defective**: it reads
with `dd bs=65536 count=1`, and a sysfs binary attribute returns at most one
page per `read(2)`, so the dump is 4096 bytes of a 65536-byte ROM. The cap was
proven on `/sys/kernel/btf/nf_conntrack` (26549 bytes: `bs=65536 count=1` gives
4096, `bs=4096` gives all 26549). **v2 is required**: `dd bs=4096` with no
count, exit 2 when the size is not 65536, sha256
`9e6c5db7853e3a58160d83c63aaee01144b20061a98a57c241188b3b6dd62a8f`, staged at
`/mega/tmp/sm750/sm750-vbios-dump` and awaiting a root install. The grant is on
the path, so replacing the body needs no sudoers change. Full bodies and the
install commands: `docs/ROOT-ACTIONS.md`.
